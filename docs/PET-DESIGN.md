## 一、定位：它不是养成游戏

传统桌宠是玩物，我们这个要做的是一件更难的事 —— **「一个一直在那里的存在」**。

所以它的所有行为都围绕一句话设计：

> **不管你怎样，我都在。**

---

## 二、红线（比要做什么更重要）

| ❌ 不要做 | 为什么 |
|---|---|
| 宠物因用户不开心而难过 | 会让用户产生**负罪感** —— "因为我不好，所以它也不开心"。陪伴类产品最致命的错误 |
| 断签掉状态 / 宠物消失 | 变成打卡任务，用户会为了"不辜负它"而勉强自己 |
| 宠物催促（"你怎么不来看我"） | 这是**情感勒索**，不是陪伴 |
| 养成游戏的数值攀比 | 偏离定位 |

**推而广之**：宠物的状态**只增不减**；它的情绪**不跟随用户情绪**。

### 用户情绪怎么接才不踩红线

| 用户情绪 | 宠物表现 | 关键 |
|---|---|---|
| 低沉（有点沉 / 疲惫 / 烦躁 / 孤单） | **什么都不做** —— 不主动说话、不弹气泡、安静待着 | 不是"它也难过"，是"**它不打扰你**" |
| 轻快 / 平静 | 可以活泼一点，偶尔摇尾巴、冒个泡 | 变的是**行为强度**，不是**它的心情** |

**一句话**：变的是**它打扰你的频率**，不是**它的心情**。

## 三、功能清单（用户能看到的）

| # | 功能 | 用户视角 |
|---|---|---|
| 1 | **领养** | 首次进主界面，右下角冒出一只小生物 →「想让我陪着你吗？」→ 选种类 + 起名（可跳过） |
| 2 | **一直在那儿** | 领养后常驻右下角，**半探出**的小状态，不抢注意力 |
| 3 | **点一下摸头** | 摇一摇 + 冒个小爱心，好感度 +1 |
| 4 | **它会说话** | 点一下弹气泡，说一句短话（"你来啦"、"（伸了个懒腰）"） |
| 5 | **它记得你** | 偶尔提起用户以前说过的事："你上次说的那只猫，还好吗" |
| 6 | **陪你多久了** | 展开后能看到「我们已经一起 47 天啦」 |
| 7 | **改名字 / 换造型** | 设置里随时可改 |
| 8 | **能拖着走** | 拖到任意位置，刷新后还在那 |
| 9 | **能藏起来** | 不想看见就收起来，**不催你、不闹你** |
| 10 | **后台能整体关掉** | 一个开关，关掉全站不显示 |

## 四、后端设计

### 4.1 数据表

```sql
CREATE TABLE `user_pets` (
  `id`               INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`          INT UNSIGNED NOT NULL,
  `species`          VARCHAR(32)  NOT NULL DEFAULT 'cat' COMMENT '种类',
  `name`             VARCHAR(32)  NULL COMMENT '用户起的名，没起就用默认名',
  `affinity`         INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '好感度，只增不减',
  `companion_days`   INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '一起待了几天',
  `last_interact_at` DATETIME     NULL,
  `created_at`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_pet_user` (`user_id`),
  CONSTRAINT `fk_pet_user` FOREIGN KEY (`user_id`)
    REFERENCES `users` (`id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='虚拟宠物（只成长，不衰减）';
```

**⚠️ 注意这里没有 `mood` 字段** —— 宠物的"表情"由前端**临时**算出来。
一旦把"心情"存进数据库，它迟早会演变成"宠物状态机"，然后就是"宠物不开心了" —— 直接踩红线。
**技术上留口子，产品上就会滑坡**，这是设计上的预防。

**⚠️ `companion_days` 只是个兜底字段** —— 日常由前端按 `created_at` 算，不做定时任务、不每天写库。

### 4.2 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/user/pet` | 读宠物信息；没有则返回 `null`，前端引导领养。**顺便带上今天该说的话**，省一次请求 |
| `POST` | `/api/user/pet` | 领养：`{ species, name }` |
| `PATCH` | `/api/user/pet` | 改名 / 换种类 |
| `POST` | `/api/user/pet/interact` | 摸头 / 投喂 `{ action }`，加好感度、更新 `last_interact_at` |
| `GET` | `/api/user/pet/memory` | 取一条**合适的**旧记忆 |

**⚠️ 设计要点：`GET /api/user/pet` 一次返回全部**（宠物信息 + 今天要说的话 + 是否该提记忆）。
这样进站只发 **1 个**请求，而不是 3 个。

### 4.3 成本控制（重要）

**宠物说话不要每次都调 AI**，否则一天几十次会烧掉不少额度。建议：

- **80% 本地语料库**：按「好感度区间 / 时间段 / 是否久未见面 / 用户最近情绪标签」分组的预设句子
- **20% 才调 AI**：**只在用户主动跟宠物对话时**，并且**每人每天设上限**（建议 20 次）

`ai_usage` 表里用 `kind: "pet"` 单独统计，方便看这块占了多少钱。

### 4.4 本地语料库设计（`lib/pet-lines.js`）

```js
export const PET_LINES = {
  firstMeet:   ["（歪着头看你）", "你终于来了"],
  today:       ["你来啦", "（打了个哈欠）", "我在这儿"],
  after3Days:  ["（伸了个懒腰）", "你来了"],        // ⚠️ 不是"你怎么才来"
  after7Days:  ["（蹭了蹭你）", "我一直在"],
  morning:     ["早", "（眯着眼睛）"],
  night:       ["还没睡呀", "（安静地待着）"],
  pat:         ["（眯起眼睛）", "（尾巴轻轻晃了晃）"],
  lowMood:     ["（安静地待在你旁边）"],            // ⚠️ 用户低落时只这样
};
```

**⚠️ 语料库每条文案都要过一遍红线**：

| ❌ 绝对不能写 | ✅ 应该写 |
|---|---|
| "你怎么三天没来看我" | "你来了" |
| "等我好久了" | "我在这儿" |
| "你今天不开心吗" | "（安静地待着）" |

**选句规则**：「多久没见 × 当前时段 × 用户情绪标签 × 好感度区间」四维分组 → 随机取一条 → **同一句 24 小时内不重复**（记录在 `localStorage`，不落库）。

## 五、前端实现要点

### 5.1 放哪、层级多少

```jsx
// 放在 app/chat/page.js 里（只在主界面出现；后台和安装页不要）
<div className="fixed right-4 bottom-24 z-40 select-none">
```

- **`fixed`** → 滚动时不动
- **`z-40`** → 高于内容、**低于弹窗（z-50）**，不会挡住确认框
- **`bottom-24`** → 避开底部输入框（用 `bottom-4` 会压到发送按钮）
- **右下角** → 和现有的**音乐浮窗（左下角）**一左一右，天然不打架

### 5.2 三个必做的细节

**① 可收起（最重要）** —— 默认"半个身子探出来"，点一下才完全展开。

**② 移动端键盘处理** —— 手机上输入法弹起时 `fixed` 元素会被顶上来盖住输入框：

```jsx
useEffect(() => {
  const vv = window.visualViewport;
  if (!vv) return;
  const onResize = () => {
    const keyboardOpen = window.innerHeight - vv.height > 150;
    setHidden(keyboardOpen);
  };
  vv.addEventListener("resize", onResize);
  return () => vv.removeEventListener("resize", onResize);
}, []);
```

**③ 可拖动** —— `onPointerDown/Move/Up`，位置存 `localStorage`。
⚠️ **必须加 `touch-none`**（`touch-action: none`），否则手机上拖动会变成滚页面。
⚠️ 拖动后要**限制在视口内**，不能拖出屏幕外找不回来。

## 六、完整数据流

```
用户进主界面
   │
   ├─ 后台 pet.enabled = false？        → 直接不渲染
   ├─ localStorage 有 solace_pet_hidden？→ 不渲染
   │
   ├─ GET /api/user/pet        ← 全站唯一的一次请求
   │     ├─ null → 弹「领养」卡片
   │     └─ 数据 → 渲染 PetWidget（含 todayLine / memoryHint）
   │
   ├─ 读取 localStorage 的拖动位置
   ├─ 空闲 3 秒 → 冒气泡（用返回的 todayLine，不再发请求）
   │
   ├─ 用户点击 → 播动画（不等接口） + POST /api/user/pet/interact
   │
   ├─ 用户主动跟它说话 → POST /api/user/pet/say
   │                     └─ 这才调 AI，记 kind: "pet" 用量
   │
   └─ 满足条件（7 天没提过 + 好感度够）→ GET /api/user/pet/memory
```

## 七、算力与性能评估 ⭐

### 7.1 结论：桌宠是**最不吃服务器**的功能

| 谁在算 | 算什么 | 负担 |
|---|---|---|
| **用户的手机 / 电脑** | **动画的每一帧**（呼吸、眨眼、摇尾巴、拖动） | 用户自己扛 |
| **服务器** | 存一行数据、发一句文本 | **几乎为零** |

**CSS 动画是在浏览器里跑的，服务器一帧都不用算。** 服务器甚至不知道用户那边宠物在动。

### 7.2 服务器实际增加了什么

| 项 | 增量 | 说明 |
|---|---|---|
| **数据库** | **1 张表 + 每用户 1 行**（约 100 字节） | 和 `user_memories` 一个量级 |
| **接口** | **1 个读 + 2 个写**，每个一次 `SELECT`/`UPDATE` | **~2ms**，比现有任何一个接口都轻 |
| **静态 JS** | **约 15 KB**（gzip 后 5-6 KB） | 用 `dynamic(ssr:false)` 后**不进首屏** |
| **图片** | **6 张 PNG/WebP，每张 20-50 KB** | **一次性下载，之后走浏览器缓存** |
| **CPU** | **≈ 0** | 没有图像处理、没有模型推理、没有视频编码 |

### 7.3 ⚠️ 关键设计：桌宠**不做轮询**

```
❌ 错误做法：前端每 10 秒问一次"宠物该说什么"
            → 一天 8640 次请求 / 用户 → 服务器会哭

✅ 我们的做法：只在三个时刻请求
   ① 进主界面时      → 一次拿全（状态 + 今天的话）
   ② 用户点它时      → 加好感度
   ③ 用户主动说话时   → 这才调 AI

   空闲时服务器完全不参与
```

**所以桌宠对服务器的压力，比"用户切一次对话"还小。**

### 7.4 服务器算力现状（诚实盘点）

桌宠不在下面这张表里，但这些**才是**真正的负载来源：

| 项目 | 负载 | 现有应对 |
|---|---|---|
| **`npm run build`** | ⚠️ **峰值最高** | `pm2 stop solace` → 构建 → `pm2 start` |
| **MySQL** | ⚠️ 中等，**曾因 OOM 被杀** | 已加 2G swap（`/swapfile`）+ `systemctl enable mysqld` |
| **AI 流式响应** | ⚠️ 占 Node 并发（等 API 时挂起） | 走外部 API，CPU 不累，但连接池只有 5 |
| **TTS** | ⚠️ 占带宽 | 走外部 API |
| **图片 base64 存库** | ⚠️ 占带宽（头像一次几百 KB） | 换取部署简单，是已知取舍 |
| **本地音频播放** | ✅ 不占服务器 | `/api/music/file` 流式返回 |

**服务器是纯 CPU 机器、没有 GPU —— 但本项目本来就不需要 GPU**：
AI 推理和 TTS 全部走**外部 API**（GLM / 小米 MiMo），服务器只做请求转发，不做任何模型计算。

### 7.5 想确认余量的话，跑这几条

```bash
nproc && uptime                        # CPU 核数 + 1/5/15 分钟负载
free -h                                # 内存和 swap
ps -o pid,%cpu,%mem,rss,cmd -C node    # Node 实际占用
ps -o pid,%cpu,%mem,rss,cmd -C mysqld  # MySQL 占用
df -h /www                             # 磁盘
```

**判读标准**：
- `uptime` 的 load average **低于 `nproc` 的核数** → 很闲
- Node 进程平时 `%CPU` **< 10%** → 很闲
- `free -h` 的 `available` **有几百 MB 以上** → 没问题

## 八、性能优化清单 ⭐

### 8.1 目标指标

| 指标 | 目标 |
|---|---|
| 新增 JS（gzip 后） | **< 6 KB** |
| 新增 CSS | **< 2 KB** |
| 图片总计 | **< 300 KB** |
| 接口耗时 | **< 50ms** |
| **空闲时的请求数** | **0** |
| 动画在手机上的 CPU | **< 1%** |
| 服务器增量 CPU | **≈ 0** |

### 8.2 前端优化

| 措施 | 做法 | 收益 |
|---|---|---|
| **不进首屏** | `const PetWidget = dynamic(() => import("@/components/PetWidget"), { ssr: false })` | 首屏 bundle 不变大 |
| **只动 GPU 属性** | 只改 `transform` / `opacity` | 不触发重排重绘，手机不烫 |
| **⚠️ 绝不改** | `width` / `height` / `top` / `left` / `margin` | 那会触发 layout，一定卡 |
| **页面不可见就停** | 见下方代码 | **切到别的标签页 → 零 CPU** |
| **尊重系统设置** | `@media (prefers-reduced-motion: reduce)` | 无障碍 + 省电 |
| **图片用 WebP** | 比 PNG 小约 30%，一样支持透明 | 省流量 |
| **静态图 + CSS 动画** | 不引 Lottie / Spine / GSAP | 少几十 KB 依赖 |
| **雪碧图（可选）** | 部件多时合成一张，减少请求数 | 少几次往返 |

**页面不可见时暂停动画**：

```jsx
const [paused, setPaused] = useState(false);
useEffect(() => {
  const onVisibility = () => setPaused(document.hidden);
  document.addEventListener("visibilitychange", onVisibility);
  return () => document.removeEventListener("visibilitychange", onVisibility);
}, []);
// 样式上：animation-play-state: paused
```

**尊重"减少动态效果"**：

```css
@media (prefers-reduced-motion: reduce) {
  .pet-anim { animation: none !important; }
}
```

### 8.3 接口优化

| 措施 | 说明 |
|---|---|
| **合并请求** | 进站只发 `GET /api/user/pet` 一次，宠物信息 + 今天的话一起返回 |
| **不轮询** | 空闲时**零请求**，这是最有效的优化 |
| **先动画面再发请求** | 点击立刻播动画，不等接口返回（手感 + 不阻塞） |
| **交互防抖** | `interact` 加 3 秒冷却，防止连点刷好感度、刷数据库写入 |
| **AI 调用限量** | `say` 的 AI 路径每人每天上限 20 次，超了自动退回本地语料 |
| **缓存静态图** | `Cache-Control: public, max-age=86400` |

### 8.4 数据库优化

| 措施 | 说明 |
|---|---|
| **唯一索引** | `uk_pet_user (user_id)` → 查询走索引，不是全表扫 |
| **单表、无 JOIN** | 宠物信息不和其他表关联查询 |
| **少写库** | 陪伴天数由前端算，不每天写一次 |
| **一行数据** | 每个用户一行，总量 = 用户数 × 100 字节 |

### 8.5 明确不做的（避免过度设计）

- ❌ 不做 WebSocket / SSE 推送宠物状态
- ❌ 不做定时任务算宠物状态
- ❌ 不做服务端渲染（`ssr: false`）
- ❌ 不做图片处理 / 压缩 / 转码（图片是画好的静态资源）
- ❌ 不引入动画库

## 九、美术需求（详细）⭐

> 这一节可以直接发给负责画模型的同学。

### 9.1 先回答"要不要动图"

**要"动"，但不要 GIF。** 用这三招组合，能把美术成本压到最低：

| 方案 | 用途 | 美术成本 | 性能 |
|---|---|---|---|
| ✅ **CSS 动画** | 呼吸（轻微缩放）、漂浮、被摸时抖一下 | **0 张额外图** | 最好（GPU） |
| ✅ **分层部件 + CSS** | 眨眼、摇尾巴、说话张嘴 | **多 3-4 张部件图** | 很好 |
| ⚠️ **序列帧 sprite** | 只有"必须逐帧"的独特动作才用 | 高（8-16 帧） | 中 |
| ❌ **GIF** | **不要用** | — | 差（256 色、透明边缘锯齿、体积大） |

**核心思路**：**一张身体 + 几个能独立动的部件**，比画十几张全身姿势省得多，效果还更活。

### 9.2 画面清单

#### 🟢 必需（少了不完整，4 项）

| 状态 | 用途 | 触发时机 |
|---|---|---|
| **待机 idle** | 常驻状态 | 默认 |
| **被摸 pat** | 眯眼 / 微微抬起 | 用户点击它 |
| **说话 talk** | 张嘴 或 表情变一下 | 冒气泡时 |
| **睡觉 sleep** | 闭眼 + 蜷起来 | 长时间没交互（>10 分钟） |

#### 🟡 推荐（明显提升表现力，2 项）

| 状态 | 用途 |
|---|---|
| **眨眼**（睁 / 闭 两帧） | 间隔 4-8 秒随机眨一次，让它"活着" |
| **初次见面**（歪头 / 探出来） | 领养那一下的仪式感 |

#### 🔵 可选（有余力再做）

- **开心**（好感度升级时）
- **倾听**（用户正在跟它说话时）
- **等待**（AI 正在生成回复时）—— 是"**安静等待**"，不是"着急"

### 9.3 ⚠️ 明确不要画的

| 不要画 | 原因 |
|---|---|
| **难过 / 哭泣 / 低落** | **红线** —— 用户情绪不好时它不能显得难过，否则用户会内疚。**这不是美术问题，是产品问题**；画得越好，用户越容易内疚 |
| **生气 / 抱怨 / 催促** | 情感勒索 |
| **生病 / 虚弱 / 掉状态** | 会被理解成"因为我没来，所以它变差了" |
| **饥饿 / 脏乱** | 变成养成游戏 |

### 9.4 强烈建议：分层导出

不管造型多特别，**这五个部件分开出图**，组合起来就能覆盖上面所有状态：

```
pet-body.png           身体（含头，主图）
pet-eyes-open.png      眼睛 · 睁
pet-eyes-closed.png    眼睛 · 闭      ← 眨眼 = 这两张切换
pet-mouth.png          嘴巴（可选，说话时换）
pet-tail.png           尾巴（单独一层）  ← CSS 单独 rotate 就能摇
pet-accessory.png      配件（耳朵 / 天线 / 光晕等造型特有的，可选）
```

**为什么这样最划算**：

| 需求 | 原本要画 | 分层后 |
|---|---|---|
| 眨眼 | 一整张"眨眼版全身" | **1 张小眼睛图** |
| 摇尾巴 | 一整张"摇尾巴版" | **1 张尾巴**（CSS 转它） |
| 说话 | 一整张"张嘴版" | **1 张嘴巴** |
| 睡觉 | 一整张"睡姿" | **闭眼 + 尾巴收起来 + CSS 缩小** |

**⚠️ 分层的关键要求**：各部件**按同一个画布尺寸导出、位置对齐、透明背景** —— 这样叠上去就是原样，不用调偏移。

### 9.5 技术规格

| 项 | 要求 |
|---|---|
| **格式** | **PNG-24 透明** 或 **WebP 透明**（同尺寸下 WebP 更小，约省 30%） |
| **导出尺寸** | **512 × 512**（前端缩到 64-96px 显示，够清晰也不浪费） |
| **多倍率** | 提供 `@1x / @2x / @3x`，或只给 512 源图由前端缩 |
| **画布对齐** | **所有部件用同一画布尺寸**，中心对齐 |
| **安全边** | 四周留 **8-10% 空白**（动画缩放 / 旋转时不会被裁） |
| **视角** | 正面 或 3/4 侧视，**全程保持一致** |
| **配色** | 建议**低饱和、偏柔和**，和站内的 `#7a9fb5` / `#e8eff2` 灰蓝调一致；别用高饱和纯色 |
| **线稿** | 细线或无线稿都可，但**边缘要干净**（不要 1px 毛边） |
| **朝向** | 建议**面朝左**（放右下角时视线朝向页面内容，不背对用户） |
| **命名** | `pet-{种类}-{部件}.png`，例如 `pet-cat-tail.png` |
| **存放** | `public/pet/` 目录 |

### 9.6 最小可行清单（时间紧的话）

只画 **3 张**就能跑起来：

```
① pet-body.png          身体（含眼睛，正常表情）
② pet-eyes-closed.png   闭眼（用于眨眼 + 睡觉）
③ pet-tail.png          尾巴
```

**效果**：呼吸（CSS）+ 眨眼（2 张切换）+ 摇尾巴（CSS 转）+ 被摸抖一下（CSS）+ 说话冒气泡（不需要图）。
**已经足够可爱，也足够"活着"了。**

### 9.7 动画参数（给画师看，让他知道图会怎么动）

| 动作 | 实现 | 参数 |
|---|---|---|
| **呼吸** | `transform: scale()` | 1 → 1.03，周期 3s，无限 |
| **漂浮** | `translateY()` | 0 → -3px，周期 4s，缓入缓出 |
| **眨眼** | 两张眼睛图切换 | 随机 4-8s 一次，每次 120ms |
| **摇尾巴** | 尾巴图 `rotate()` | 旋转原点设在尾巴根部，-8° ↔ +8°，周期 0.6s |
| **被摸** | `translateY` + `rotate` | 弹一下，300ms |
| **睡觉** | 身体 `scale` 缩小 | 0.95 倍 + 切闭眼 |
| **整体出现** | `opacity` + `scale` | 0 → 1，400ms |

**⚠️ 全部只动 `transform` 和 `opacity`** —— GPU 加速，不会卡。

## 十、实现顺序（每步都能单独跑起来）

| 步骤 | 内容 | 依赖 | 规模 |
|---|---|---|---|
| **1** | 静态悬浮：一张图 + `fixed` 定位 + 可收起 | **不需要后端** | 小 |
| **2** | 点一下弹气泡说话（本地语料） | 不需要后端 | 小 |
| **3** | 接数据：陪伴天数、好感度、领养流程 | 需要 4.1 + 4.2 | 中 |
| **4** | 接记忆：偶尔提起用户以前说过的事 | 复用 `user_memories` | 小 |
| **5** | 拖动 + 位置记忆 | 不需要后端 | 小 |
| **后台** | `settings.pet` 分组 + 一个 tab | 同「背景音乐」写法 | 小 |

**后台设置分组**：

```js
pet: {
  enabled: true,          // 总开关
  defaultSpecies: "cat",
  useAi: true,            // 关掉就纯本地语料（零成本）
  interactCooldownSec: 3, // 防止连点刷好感度
}
```

## 十一、最容易做错的三个地方

1. **挡住输入框** → 用 `bottom-24`，并在键盘弹起时藏起来
2. **默认就全展开** → 会很烦，默认收起、主动点才展开
3. **进首屏 bundle** → 用 `dynamic(..., { ssr: false })`
