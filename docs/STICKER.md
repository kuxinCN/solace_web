# AI 表情包（贴纸）功能说明

用户连续表达同类情绪时，AI 会在回复末尾**自然地**附一张治愈系贴纸，没有任何文字说明。
贴纸由服务端的「情绪节流引擎」统一决策，**宁少发，不滥发**。

改这块代码 / 换贴纸素材 / 调触发频率前，请先读一遍本文档。

- 核心代码：[`lib/sticker-engine.js`](../lib/sticker-engine.js)（判断 + 计数 + 概率 + 冷却，纯逻辑可单测）
- 分类与素材的读写：[`lib/sticker-store.js`](../lib/sticker-store.js)
- 服务端接入：[`app/api/chat/route.js`](../app/api/chat/route.js)
- 前端接入与渲染：[`app/chat/page.js`](../app/chat/page.js)
- 素材目录：`public/stickers/<分类>/`
- 后台管理：管理后台的「**表情包**」页（`app/admin/page.js` + [`components/StickerPanel.jsx`](../components/StickerPanel.jsx)），
  接口在 `app/api/admin/stickers/**`；用户端读的是公开接口 [`app/api/stickers/route.js`](../app/api/stickers/route.js)

> ⚠️ **2026-10 起：分类、词表、优先级、素材全部可以在后台增删改，数据库是唯一事实来源。**
> 本文档讲的是**机制**（概率、冷却、间隔、标记协议）；**具体有哪些分类、靠哪些词判定**，
> 请直接看后台页面 —— 代码里只留一份**出厂默认** `DEFAULT_SPEC`
> （用途只有两个：数据库读不到时兜底 + 首次播种的种子）。
> 本文档里凡是写"内置 XX"的说法，指的都是 `DEFAULT_SPEC` 的出厂值。

## 一、一句话流程

```
用户发言
  → 读一次分类配置（后台配的 spec；进程内缓存 30 秒，后台改完立刻失效）
  → 情绪判断（关键词秒判，判不出才调轻量 AI，2.5s 超时即放弃）
  → 该对话、该情绪计数器 +1
  → 按累计句数查概率掷骰（0% / 40% / 100% 保底；深夜放宽的分类 60% / 100%）
  → 再过两道硬门槛：该情绪 15 分钟冷却、任意两张贴纸间隔 ≥ 5 轮
  → 中奖：流末下发一条独立 SSE 事件 {sticker:分类}
  → 前端把 [sticker:分类] 拼进消息末尾落库，渲染成 AI 气泡下方的圆角小图
```

情绪判断与主对话的文字流式输出**并行发起**，只在流末取结果，不增加首字延迟；
任何一步异常都静默退回"不发贴纸"，绝不影响正常聊天。

## 二、情绪判断

### 2.1 出厂内置四个分类（**分类可以在后台增删**）

后台里一个分类就是一行配置：情绪键（程序内的身份）、标记名（= 素材目录名）、关键词词表、
优先级、是否深夜放宽、是否纳入 AI 判定、是否可主动发图。出厂内置这四个
（播种**只在表为空时**做一次 —— 删掉的不该被下次部署加回来）：

| 情绪键 | 含义 | 标记名 / 素材目录 | 优先级 | 备注 |
|---|---|---|---|---|
| `comfort` | 难过、烦躁、焦虑、生气、需要安慰 | `comfort` | 10 | |
| `sleepy` | 累、困、疲惫、失眠 | **`sleep`** | 20 | 深夜放宽 |
| `happy` | 开心、分享好事 | `happy` | 30 | |
| `daily` | 日常闲聊 / AI 判不明 | `daily` | 999 | **只兜底、永不主动触发**（`triggerable = 0`） |

> ⚠️ `sleepy` 对应目录 `sleep` 是**历史命名**，已经写进历史消息了，别改。
> 标记名（= 目录名）**建好之后一概不能改**：改名会让旧消息里的 `[sticker:...]`
> 指向一个不存在的目录 —— 用户看到的是一个空白位置，而且只在翻旧消息时才发现。
> 真要改名：建个新分类 → 素材重新登记 → 停用旧的。
>
> ⚠️ **一个分类名下没有任何"启用中"的素材时，引擎不会发它**（直接跳过，连计数都不做）。
> 所以"建了分类忘了传图"的表现是"这个情绪不发贴纸"，这是故意的：
> 宁可静默不发，也不发一个前端找不到图的空标记（那种问题最难查）。

### 2.2 关键词优先（默认路径，毫秒级、零成本）

- 关键词表**在后台**（管理后台 → 表情包 → 展开某个分类 → 关键词，一行一个）；
  出厂内置那几组在 `lib/sticker-engine.js` 的 `DEFAULT_SPEC`。刻意"少而准"：
  - comfort：难过、难受、烦、焦虑、崩溃、想哭、委屈、孤独、撑不住、气死了……
  - sleepy：好累、好困、疲惫、失眠、熬夜……（单字"累/困"放在词表最后，减少误判）
  - happy：开心、太好了、好棒、哈哈、笑死、考上、升职……
- **否定词排除**：关键词前一个字是「不 / 没 / 别」时该命中作废
  （"我不累"、"今天不困"不算；但"虽然不累但是有点烦"仍能命中后面的"烦"）。
- 一条消息命中多个分类时，按**优先级**（`priority`，数字小的先发；内置 comfort 10 / sleepy 20 / happy 30）。
  后台改词表时如果和别的分类撞了同一个词，面板会提示（只提示、不拦 —— 最终发哪张由优先级决定）。
- 关键词判不出来（如"在吗""今天周三"）→ 返回 `null`，进入 AI 兜底。
- ⚠️ 关键词**加得太宽会误发**（"多则误发、少则漏判"，这套词是调了很久才收敛的）。
  改完保存**即生效**（引擎侧那份配置缓存 30 秒，后台每次写操作都会立刻让它失效），
  不用改代码、不用重启，用户端刷新页面就按新词表判。

### 2.3 轻量 AI 兜底（少数句子才走）

- 仅当关键词未命中 **且** 后台配了 AI apiKey 时调用，复用主对话同一份配置，不额外查库。
- 提示词**按后台的分类动态拼**：只列勾了「关键词判不出时交给 AI 判」的分类名 + `unknown`；
  分类名用的是后台填的**分类名称**（所以把名字起清楚一点，模型判得更准），`maxTokens = 512`。
- **5 秒超时**（`Promise.race`）、模型报错、返回 daily/unknown → 一律按 `null` 处理，
  本轮不计数、不发贴纸。贴纸是锦上添花，不等慢判断。
- ⚠️ **这两个数字都是踩坑定的，别随手压小**（2026-10-03 实测线上 `mimo-v2.6-flash-free`）：
  - 它是**推理型模型**：`maxTokens` 给小了（16 / 64），额度先被 `reasoning_tokens` 吃光，
    结果是 `finish_reason=length` 而 `content` 是**空字符串** —— 300 起才稳定答出类别名；
  - 答完要 **2.8~10.3 秒**，所以原来的 2.5 秒上限**几乎必然超时**，情绪永远判不出来。
  - 关键词命中的句子走本地匹配（毫秒级），**完全不受这两条影响**。

## 三、概率递增触发（核心规则）

计数器记的是"该情绪**从中奖归零之后**连续累积了几句同类情绪的话"，
每来一句 +1，然后按下表掷骰：

### 3.1 白天（06:00–23:00）—— comfort / happy / sleepy 三张通用一套表

| 该情绪累计句数 | 触发概率 | 行为 |
|---|---|---|
| 第 1 句 | **0%** | 必不发（避免"一说情绪就甩图"） |
| 第 2 句 | **40%** | 随机：可能当场给惊喜，也可能继续等 |
| 第 3 句 | **100%** | 保底必发 |
| 第 4 句及以后 | 100% | 门槛（冷却/全局间隔）一解除就补发 |

### 3.2 深夜（23:00–06:00）—— 只有勾了「深夜放宽」的分类放宽（内置只有 sleepy）

| sleepy 累计句数 | 触发概率 |
|---|---|
| 第 1 句 | **60%** |
| 第 2 句 | **100%** 保底 |

深夜的 comfort / happy 仍走白天表（3.1），不放宽 —— 这是分类上的一个开关，
后台可以给任何分类打开（比如"深夜的陪伴"）。

### 3.3 随机是怎么实现的

- 一句标准 `Math.random() < probability`：
  - 第 2 句 `Math.random() < 0.4`，约 40% 的对话在第 2 句收到贴纸；
  - 没摇中（约 60%）就保留计数进入下一轮，第 3 句概率为 1，
    `Math.random() < 1` 恒成立 → **3 句内必出 1 张**是数学保证，不是循环重试。
- 概率表**仍然是全局一张**（不分分类）：`normalProb`（白天）= `[0, 0.4, 1]`、
  `lateNightProb`（深夜）= `[0.6, 1]`，查档函数
  `triggerProbability(cat, count, lateNight, spec)`，想在代码里调频率只改这两个数组
  （在 `DEFAULT_SPEC` 里）。
  ⚠️ **刻意没有做成"每个分类一张表"** —— 分类可以加到十几个，每类一张表会让调参入口
  彻底失控（§八 那张速查表就没法看了）。
- 单测可给 `applyTurn(state, emotion, {rand})` 注入随机源做确定性验证；
  线上用默认的 `Math.random`。

### 3.4 中奖后立即归零（不连中）

中奖的一刹那：**该情绪计数立即清 0** + 置该情绪 15 分钟冷却 + 记录全局贴纸轮次。
所以下一句同情绪的话是"新周期的第 1 句"，概率重新从 0% 开始 —— 第 2 句和第 3 句不可能连续中。

### 3.5 两道硬门槛（优先级高于概率）

1. **同情绪 15 分钟冷却**：发出后 15 分钟内，该情绪即使计数攒到 100% 档也不掷骰、不发；
   计数继续保留，冷却一过（且全局间隔满足）即补发。
2. **全局 5 轮间隔**：任意两张贴纸之间至少隔 5 轮用户发言
   （第 3 轮发了一张，最早第 8 轮才能发下一张），与情绪类型无关。

> "5 句内最多 2 张"由「归零重来 + 15 分钟冷却 + 全局 5 轮间隔」自然保证，
> 实测比这个上限更严格（相邻两张至少隔 5 轮），不需要额外计数器。

### 3.6 多情绪同轮的优先级

一轮里如果多个分类都"有计数且摇中"，按**优先级**（`priority`，数字小的先发）只发一张。
高优先级情绪这轮没摇中（例如第 2 句落在 40% 之外）**不挡**低优先级情绪的保底，
各情绪的计数与掷骰相互独立。

## 四、计数器存在哪

- **后端进程内存**里的一个 `Map`（`lib/sticker-engine.js` 模块级变量 `states`），
  **不建表、不写 Redis、不写 localStorage**。
- 键：`` `${userId}::${conversationId}` `` —— 用户维度 + 对话维度双重隔离，
  切换对话 / 切换账号都不可能串计数。
- 每个对话的状态：

  ```js
  {
    turn: 0,                    // 该对话用户发言总轮次（只增）
    counts: {},                 // 各分类"归零后连续累计句数"
    cooldownUntil: {},          // 各分类冷却到期时间戳
    lastStickerTurn: null,      // 上一次发贴纸的轮次（全局间隔用）
    lastSeen: 0,                // 最近访问时间（懒淘汰用）
  }
  ```

- ⚠️ `counts` / `cooldownUntil` 是**空对象懒建**的（不是写死三个 key）：
  分类是后台可增删的。状态里也**不存分类清单** —— 分类每轮从 spec 传入，
  所以后台删掉一个分类后，残留在 `counts` 里的那个计数不会被任何人读到
  （除非将来建一个同键名的分类，那会继承这份旧计数，无伤大雅）。

- 生命周期：24 小时无消息的对话懒淘汰；条目硬顶 5000 条，超了淘汰最久未访问的。
- **服务重启计数清零**：这是有意的。计数器是节流用的临时状态，
  丢了顶多少发/重攒几张贴纸，用户无感知；贴纸本身随消息落库，历史记录不受影响。
- 部署注意：状态不跨进程共享，**必须单实例运行**（本项目 pm2/宝塔本来就只起一个实例）。

## 五、贴纸怎么进入消息流（不改文字流、不碰 TTS）

1. `/api/chat` 在发起主对话 AI 请求前，**并行发起**贴纸决策（不 await）。
2. 文字 SSE 照常 `data: {"delta":"…"}` 流式输出，贴纸完全不参与文字流。
3. 文字流收尾（处理完 RISK/MEMORY 标记 replace）后，才 `await` 贴纸决策结果；
   中奖则多发一条事件：`data: {"sticker":"comfort"}`，最后才 `[DONE]`。
4. 前端 `askAI` 把文字与贴纸分开收：`onDelta` 全程只收到纯文字；
   贴纸分类单独返回 `{ text, sticker }`。
5. 前端在落库前把标记拼到正文最后一行：

   ```
   我在这儿陪你。
   [sticker:comfort]
   ```

   先 `setMessages` 让贴纸立即上屏，再随消息一起 POST 落库；
   渲染层 `parseStickerMark()` 会把标记行剥离成纯文字 + 气泡下方的贴纸图片，
   **刷新页面 / 重进对话从数据库读历史，贴纸照常显示**。
6. 模型如果私自输出 `[sticker:xxx]`（旧人格提示词残留），服务端用
   `stripStickerMarkers()` 统一剥离（流式期间露过的用 `{"replace": …}` 收回），
   贴纸的唯一合法来源是节流引擎。
7. 非流式分支返回 JSON 多一个 `sticker` 字段。

### 特殊场景

| 场景 | 行为 |
|---|---|
| 重新生成（regenerate） | 是重放旧消息、不是新发言：payload 带 `regenerate:true`，服务端**不计数、不触发贴纸** |
| 表情包总开关 | 后台「表情包设置 → 启用表情包」关闭后，服务端连情绪判定都不做（省一次判定 + 两次查库），直接不发 |
| 日记回应 | 用「日记标题 + 正文」作为情绪判断文本（`emotionText`），计数仍归当前对话 |
| TTS 朗读 | 手动喇叭喂给 TTS 的是 `parseStickerMark(content).text` 纯文本；自动朗读走 `onDelta` 本就纯文字——贴纸标记永远不会被念出来 |
| 拼给模型的历史 | 构建 messages 时用 `parseStickerMark(m.content).text`，历史贴纸标记不会喂回模型 |

## 六、贴纸素材规范（换图 / 加图必读）

### 6.1 现状

```
public/stickers/
├── comfort/微信图片_20260921154311_122_1.jpg   (≈73 KB)
├── happy/微信图片_20260921154310_121_1.jpg     (≈96 KB)
├── sleep/微信图片_20260921154309_120_1.jpg     (≈87 KB)  ← sleepy 情绪用这个目录
├── daily/微信图片_20260921154308_119_1.jpg     (≈65 KB，目前不主动触发)
├── blue_butterfly.png / blue_butterfly_side.png  ← 桌宠素材，与表情包无关，勿动
```

> 上面是出厂时磁盘上的样子。分类与素材现在**以数据库为准**（后台可增删），
> 磁盘上还可能有后台上传的新目录 / 新文件；桌宠自己上传的形象在 `public/pets/`。

### 6.2 图片要求

| 项 | 要求 |
|---|---|
| 格式 | `.jpg` / `.png` / `.webp` 均可；想要透明底/圆角留白用 PNG 或 WebP |
| 画面比例 | **正方形（1:1）或近正方形**，主体居中；前端按固定宽度等比缩放，不裁图 |
| 尺寸 | 渲染宽 **100px、最大 120px**；素材建议提供 **240×240 或更大**（高分屏不糊），单边不超过 512px |
| 文件体积 | 单张建议 **≤ 200 KB**（当前四张 65–96 KB），太大会拖慢消息流末尾的加载 |
| 风格 | 治愈系、柔和、低攻击性；情绪表达一眼可辨；**图片内不要出现大段文字 / 水印 / 二维码** |
| 圆角 | 圆角由前端 CSS 裁（`rounded-2xl`，约 16px），素材本身方图即可；透明底也兼容 |
| 数量 | 每个分类可放多张，前端会在该分类内随机挑（见 6.3）；建议先每类 3–5 张，宁缺毋滥 |

### 6.3 新增 / 替换贴纸的步骤

**推荐做法（后台上传，什么都不用改代码）**：

1. 管理后台 →「表情包」页 → 展开对应分类 →「上传图片」；
   图片会存到 `public/stickers/<分类目录>/`，并自动登记进 `stickers` 表、立即可用。
   - 限制：≤ 2MB，`.png / .jpg / .jpeg / .webp / .gif`，**会校验真实文件头**
     （改名成 `.jpg` 的 SVG/HTML 会被拒收）。
   - **保留原文件名**（只做安全清洗）—— 素材目录是运维直接进磁盘看的地方，
     全变成随机串等于把目录变废。同名文件**不覆盖**，自动追加时间戳
     （覆盖会毁掉已经发出去的历史贴纸）。
2. 刷新用户端页面即可。不需要改数据库、不需要改引擎、**也不需要改前端代码**；
   标记协议 `[sticker:<分类>]` 不变。

**手工丢文件的老流程（仍然可用）**：

1. 把图片放进 `public/stickers/<分类目录>/`（目录名 = 后台那个分类的「素材目录名」）。
2. 回后台 → 展开该分类 →「**重新扫描目录**」→ 目录里没登记过的图会被批量补登记。
   ⚠️ 不做这一步，图片就是"看不见的图"：表里没有记录，用户端永远不会用它。
3. 访问一次 `http://<站点>/stickers/<分类>/<文件名>` 确认 200 可打开
   （文件名含中文时记得 URL 编码）。

> 前端资源表 `STICKER_MAP` 现在是**接口驱动**的：进站拉一次 `GET /api/stickers`
> 就地改写它（拉不到就保留内置那四张兜底）。所以"加图要手动登记到 `page.js`"
> 这条老规矩**已经作废** —— 那是浏览器读不了服务器目录的年代留下的办法。
>
> 同一分类多张时**随机挑一张**；同一条 AI 回复内固定不换（`stickerPickRef` 缓存），
> 且最近 3 张不重复（`recentStickersRef`）。

### 6.4 想新增一个情绪分类（比如 angry）

**现在只需在后台点几下，不用改代码**：

1. 管理后台 →「表情包」→「新增分类」，填四样：
   - **情绪键**（程序内身份，小写字母/数字/下划线，例 `angry`）；
   - **素材目录名**（= 标记名 `[sticker:angry]`，留空默认同情绪键；**建好不可改**）；
   - **分类名称**（会出现在 AI 兜底提示词里，例 `生气`）；
   - **优先级**（数字小的先发，built-in 是 10/20/30/999，新分类建议插到合适的位置）。
2. 展开这个分类 → 传图（或把图丢进 `public/stickers/<目录名>/` 再「重新扫描目录」）。
3. 填关键词词表（一行一个），按需勾选「可以主动发图 / 交给 AI 判 / 深夜放宽」。
4. 用户端刷新页面即生效。

> ⚠️ 历史版本要改四处（引擎 `KEYWORDS` + `PRIORITY` + `STICKER_CATEGORY`、前端 `STICKER_MAP`、
> AI 提示词枚举），少一处就静默失效。2026-10 那次改造把这几处全部收进数据库配置了 ——
> 如果你在旧文档/旧笔记里看到"要改四处"，那是改造前的说法。
>
> 新增分类后**别忘了传图**：没有启用素材的分类不会发图（见 §2.1 的提示）。

## 七、手动验收话术

> 下面这些是**机制层**的用例。2026-10 改造（分类改配置化）之后，其中绝大多数已经在一次
> **41 项纯逻辑回归**里被覆盖过：关键词命中与否定词、概率表三档、第 3 句保底、中奖归零、
> 15 分钟冷却、5 轮全局间隔、深夜表、daily 永不触发、没有素材的分类不发图、
> 自定义分类的优先级与标记映射。需要**真的发消息**才能验的是：对话隔离、重新生成、TTS。

| 用例 | 操作 | 预期 |
|---|---|---|
| 3 句保底 | 同一对话连发「我好难过」「心里难受」「有点崩溃」 | 第 1 句必无；第 2 句约 40% 概率有；第 3 句必出 Comfort |
| 随机性 | 反复开新对话测 10 次以上 | 能观察到有时第 2 句发、有时第 3 句发 |
| 归零重算 | 第 2 句中奖后，下一句继续说难过 | 新周期第 1 句 0%，不会连发 |
| 15 分钟冷却 | 中奖后 15 分钟内再说 3 句难过 | 不再发 |
| 对话隔离 | A 对话攒难过，去新建的 B 对话攒开心 | 两边计数互不影响，Happy 照常触发 |
| 深夜放宽 | 把设备时间改到 23:00 后说一句「好累」 | 第 1 句 60% 概率出，第 2 句必出 Sleepy（标记 `sleep`） |
| 全局间隔 | 不同情绪交替连续触发 | 任意两张贴纸间隔 ≥ 5 轮对话 |
| 重新生成 | 对任一条 AI 回复点重新生成 | 不补发贴纸、不影响计数 |
| TTS | 对带贴纸的回复点喇叭 | 只念文字，不念任何标记 |
| **后台新增分类即可发图** | 后台新增分类 `angry`（名称"生气"、优先级 5）→ 传一张图 → 用户端刷新，连发三句「气死我了」 | 第 3 句必出刚传的那张；**全程没改过一行代码**（标记 `[sticker:angry]`） |
| **空分类不发图** | 新建一个分类但不传图，关键词设成一句好触发的话，用户端说三句 | 永远不发（引擎跳过没有启用素材的分类），其它分类照常 |
| **停用素材即停发** | 把某分类唯一的素材停用 | 该分类立刻不再发图（引擎按"没有可用素材"处理） |
| **总开关** | 后台关掉「启用表情包」 | 聊天完全不再出现表情包（连判定都不做）；打开即恢复 |
| **改词表立即生效** | 给 comfort 的关键词加一个「心里堵」→ 保存 | 用户端刷新后说「心里堵」即按 comfort 计数（不用重启、不用等） |

## 八、调参与测试速查

**可以在后台改（改完用户端刷新即生效，不用重启）**

| 想改什么 | 在哪里（管理后台 → 表情包） |
|---|---|
| 有哪些情绪分类 | 右上「新增分类」/ 分类行右侧「删除」 |
| 每类靠哪些词判定 | 展开分类 → 关键词（一行一个，逗号/顿号也能分隔） |
| 同轮先发谁 | 展开分类 → 优先级（数字小的先发） |
| 某类深夜是否放宽 | 展开分类 → 深夜放宽 |
| 某类是否交给 AI 判 | 展开分类 → 关键词判不出时交给 AI 判 |
| 某类是否主动发图（如 daily） | 展开分类 → 可以主动发图 |
| 分类 / 单张素材启停 | 分类行右侧「停用」/ 素材缩略图下的「停用」 |
| 素材图片 | 展开分类 → 上传图片 / 重新扫描目录 |
| 整个表情包开关 | 上面的「表情包设置」→ 启用表情包 |

**只能在代码里改（要重新构建部署）**

| 想改什么 | 改哪里（`lib/sticker-engine.js` 除非另有说明） |
|---|---|
| 各句触发概率（全局一张表） | `DEFAULT_SPEC.normalProb`（白天）/ `lateNightProb`（深夜） |
| 深夜时段 | `isLateNight()`（`h >= 23 || h < 6`） |
| 同情绪冷却时长 | `EMOTION_COOLDOWN_MS`（默认 15 分钟） |
| 两张贴纸全局间隔 | `GLOBAL_TURN_GAP`（默认 5 轮） |
| AI 兜底超时 / 回答上限 | `detectEmotion(text, config, timeoutMs, spec)` 默认 5000ms；`maxTokens: 512`。⚠️ 推理型模型额度给小了会返回**空 content**，见 §2.3 |
| 内存容量 / 淘汰 | `MAX_STATES`、`STATE_TTL_MS` |
| 分类配置的缓存时长 | `lib/sticker-store.js` 的 `SPEC_TTL_MS`（默认 30 秒） |
| 出厂默认分类 | `DEFAULT_SPEC`（兜底用 + 首次播种的种子） |

- 引擎是无 DB 依赖的纯逻辑模块，可直接被 Node 以 ESM 导入做单测
  （`applyTurn(state, emotion, {now, lateNight, rand}, spec)` 支持注入随机源与时间；
  不传 `spec` 就用 `DEFAULT_SPEC`，所以老写法照旧能跑）。
- ⚠️ **改 `DEFAULT_SPEC` 不会影响已经建好的库**（和"配置存在数据库里"那条老坑一样）：
  线上要同步改，得去后台改；想让出厂值重新生效，得清空 `sticker_categories` 重新播种。
- 改完至少验证：概率表三档、第 3 句保底、中奖归零、深夜表、15 分钟冷却、
  5 轮全局间隔、优先级、对话隔离、没有素材的分类不发图。
- 排查"为什么没发贴纸"的顺序：
  ① 这个分类在后台是不是停用了 / 有没有**启用中**的素材
  ② 这句话情绪判出来了吗（关键词 / AI）；关键词没命中时，看最后一条"兜底为何没兜住"
  ③ 累计到第几句
  ④ 这轮随机摇中了吗
  ⑤ 是否在该分类 15 分钟冷却里
  ⑥ 距上一张够 5 轮吗
  ⑦ 「启用表情包」总开关是不是关着。
  ⑧ 兜底为何没兜住：模型是不是**推理型**（思考 token 吃光 `maxTokens` → `content` 空），
     或者答得比 5 秒还慢 —— 两种情况都会按"没情绪"处理。
     📌 想让它更少依赖兜底，最稳的是**往分类关键词表里加词**（后台可改，零成本、毫秒级）：
     关键词命中的句子根本不走 AI。
