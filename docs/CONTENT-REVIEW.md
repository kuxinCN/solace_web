# 数据审核（内容安全）

> 用户上传的头像、背景图、昵称、签名会**立刻生效**，同时被标上「未审核」，
> 由后台或定时任务批量交给 AI 判定：合规就清掉标记，违规就改回后台配置的默认值。

## ⚠️ 审核范围（先看这个，别搞错）

| 内容 | 审不审 | 说明 |
|---|---|---|
| 昵称 / 个性签名 | ✅ **审** | 用户填的，别人看得到 |
| 头像 / AI 头像 / 聊天背景 / 我的页背景 | ✅ **审** | 同上 |
| **日记** | ❌ **不审** | **日记是私密内容，只有用户自己看得到 —— 审它等于背叛用户信任**。日记只做「AI 情绪打标」（那是给用户自己看的标签，不是审查） |
| **会话标题** | ❌ 不审 | AI 自动生成的，不是用户输入 |
| 聊天消息 | ❌ 不审（有另一套） | `lib/content-guard.js` 在**发给 AI 之前**实时判定，但**不截断** —— 见下面的「聊天消息的安全处理」 |

**一句话**：审核的对象是「**别人能看到的、且是用户自己填的东西**」。

### 聊天消息的安全处理（⚠️ 和上面这套审核是**两条线**）

上面那套「数据审核」是**异步、批量、事后**的（头像 / 昵称这些）；
聊天消息走的是**同步、单条、事前**的另一条线，在 `lib/content-guard.js`。

**原来的行为**：命中安全词 → **不调 AI**，直接返回固定话术 + 热线。

**现在的行为**：三层判定，**只有紧迫危机才截断**：

| 命中 | 处理 |
|---|---|
| **紧迫危机**（危机词 + 计划/时间表达，如「今晚」「已经买了」「写了遗书」） | **截断**，返回干预话术 + 热线，不走 AI |
| **风险表达（非紧迫）** / **安全词**（伤人 / 违法） | **安全模式** —— 正常调 AI，附加安全指令要求"先共情、再温和引导"，**回复里没提到热线会自动补一句** |
| **压力词** | 只触发压力测算，**不影响回复** |

**为什么要改**：固定话术是"关门"，而说那句话的人恰恰是最需要被接住的时候 ——
让 AI 接着聊、先回应他说的具体内容，比甩一句标准答案好得多。

**⚠️ 词表现在也可以在后台改了**（原来是硬编码的 `CRISIS_PATTERNS`）：
「内容安全与压力」页的「统一词表」区管理六张表（自伤倾向 / 伤人 / 违法 + 压力词三档），
改完保存**立即生效，不用重启**。

⚠️ 还有一层「疑似命中交给 AI 判」的机制：词表命中里**只有"前缀+后缀组合"出来的**
（想 + 死）才让对话 AI 判语义，它在回复里带 `[RISK:no]` 才撤掉热线；
**完整短语命中**（遗书 / 割腕）直接进安全模式，**不给 AI 翻案的机会**。
细节见 `lib/suspected-store.js` 的文件头说明。

## 一、为什么要做成异步

用户改资料是高频操作，**不能卡在审核上**（等 AI 判定要几秒到几小时）。
所以流程是「先放行、后审核」：

```
用户改昵称 / 传头像
        │
        ├─ ① 立刻写库，前端立刻看到效果   ← 用户感受不到审核的存在
        │
        └─ ② 同时入审核队列 + 给 users 打上「未审核」tag
                    │
                    ▼
        攒够一批（或点了「立即提交」/ 定时任务触发）
                    │
                    ▼
        提交给审核 AI（小米 MiMo，批量推理）
                    │
                    ▼
              ⏳ 延迟返回结果
                    │
                    ▼
        拉取结果（点「拉取结果」或定时任务自动收）
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
     合规 ✅                  违规 ❌
  清掉「未审核」tag      该字段改回后台配置的默认值
```

## 二、用户视角

| 操作 | 用户看到什么 |
|---|---|
| 改昵称 / 签名 / 头像 / 背景 | **立刻生效**，没有任何等待或提示 |
| 内容合规 | 无感（后台清掉标记，用户看不到） |
| 内容违规 | 过一段时间后，那个字段**变回默认值**（比如昵称变成"用户"，头像变回默认头像） |

**用户不会收到"你违规了"的弹窗** —— 这一点是刻意的：这个产品是陪伴场景，
在用户情绪本就不好的时候弹一个"你的内容违规了"，是很伤人也很没必要的事。

## 三、后台视角

**后台 → 「数据审核」**（在「内容安全」右边）

### 顶部：审核运行状态

- **状态卡片**：待提交 / 已提交（等结果）/ 合规 / 违规已处置 / 失败·待人工
- **三个按钮**：
  | 按钮 | 作用 |
  |---|---|
  | **刷新** | 重新读一遍状态 |
  | **拉取结果** | 查一遍已提交的批次，把完成的收回来并对违规内容执行处置 |
  | **立即提交** | 把当前所有「待提交」的内容**立刻**上传给审核 AI |

### 批次记录

每次提交对应一行，能看到：批次 id / 方式（批量·逐条）/ 状态 / 条数 / 结果统计 / 提交时间。
失败的批次会在下面用红字列出**上游返回的原始错误**，方便定位。

### 审核记录

列出最近 60 条，可按「全部 / 未完成 / 待人工 / 违规」筛选，每条可以：

- **查看内容** —— 弹出详情，图片直接显示缩略图，文本显示正文
- **通过** —— 人工判定合规，清掉标记
- **驳回** —— 人工判定违规，**该字段立刻改回默认值**

## 四、配置项说明

**后台 → 「数据审核」→ 配置区**

### 审核 AI

| 字段 | 说明 |
|---|---|
| **启用数据审核** | 总开关。关掉后不再审核（已攒的待审内容会留在队列里） |
| **服务商备注** | 仅记录，不影响调用 |
| **接口地址（逐条 / 对话）** | 小米 MiMo 填 `https://api.xiaomimimo.com/v1`。**测试连接、拉取模型、逐条模式**都走这个地址 |
| **批量推理接口地址** | ⚠️ **是独立域名，和上面那个不是一回事**：形如 `https://batch-api-{region}.xiaomimimo.com/v1`，要去小米控制台的「**批量推理**」页面获取后填进来。<br>留空的话批量提交必然失败 —— 程序会自动降级为逐条模式，功能不受影响，但拿不到批量推理的**五折价**和闲时调度 |
| **API Key** | 要求和对话 AI 一样。程序对小米域名**同时发送 `Authorization: Bearer` 和 `api-key` 两个头** —— 因为小米的批量文档用前者、对话 / TTS 用后者，两个都发最稳 |
| **模型名** | ⚠️ 批量推理**只支持 `mimo-v2.6-pro` 和 `mimo-v2.6-flash`**，而且**模型名必须全小写**。**点右侧箭头看候选**，也可以点「拉取模型」自动获取 |
| **审核方式** | `批量推理`（一次一批，延迟返回） / `逐条调用`（立刻出结果） |
| **最长等待时间** | ⚠️ **实测结论：接口只认 `24h`。**<br>填 `168h`（7 天）这类值，服务端会直接返回 **HTTP 500 internal_error**，提交就挂在「创建批次」这一步（上传文件那步其实是成功的）。<br>文档里「控制台可设 1-14 天」那句**只对控制台页面有效**，接口不吃这套。<br>**程序已经做了兜底**：先用你填的值试，失败且不是 24h 就自动退回 24h 重试一次 —— 所以填错也不会挂。但建议就保持 `24h` |
| **批量不可用时自动降级为逐条** | **建议开着**。批量接口的协议如果和 OpenAI Batch 不一致，提交会失败；开着这个就自动改成逐条，审核不会卡死 |
| **连图片一起送审** | 关掉后头像 / 背景**完全不送 AI**，只进后台人工队列（昵称和签名始终会送审） |
| **图片任务怎么处理** | ⚠️ **图片不能进批量推理** —— 多模态消息体会让整个批次在**创建阶段**就失败（HTTP 500 internal_error），**一条图片就能拖垮整批**。<br>所以批量模式下图片只能二选一：<br>· **进后台人工队列**（默认，不花 AI 额度）<br>· **用「逐条调用」单独审**（会花钱，但能自动处理 —— 逐条是单条调用，互不牵连）<br>⚠️ 如果「审核方式」选的是「逐条调用」，这个设置不起作用（那时图片跟文本一起走逐条） |
| **每次最多提交条数** | 1-100，默认 20 |
| **逐条模式超时** | 默认 120 秒 |
| **审核记录保留天数** | 默认 30 天，超出的由 `scripts/cleanup.mjs` 清理 |
| **审核提示词** | 发给审核 AI 的系统提示词。默认版本已经把边界写清楚了（见下） |

**默认提示词的两个关键设计**：

1. **明确列出"必须判合规"的情况** —— 表达负面情绪、说"不想活了"这类，
   **是求助信号，不是违规**。这是这个产品的底线：不能因为用户情绪不好就惩罚他。
2. **解析不出来时一律按合规处理** —— 把用户资料重置是很重的动作，
   宁可放过一条，也不能因为模型输出格式不对就误伤。

### 默认值配置（违规后回填）

| 字段 | 违规后 |
|---|---|
| **默认昵称** | 昵称改回这个（默认"用户"） |
| **默认签名** | 留空 = 清空签名 |
| **默认头像** | 选一张图；留空 = 用前端自带的默认头像 |
| **默认 AI 头像** | 同上 |
| **默认聊天背景** | 同上 |
| **默认「我的」页背景** | 同上 |

**图片怎么存**：选图时会在浏览器里**缩到 512px 并转成 data URL** 存进配置
（不落磁盘，和用户上传的格式一致，处置时直接写库就行）。

## 五、数据库

### `users` 表新增两列

```sql
`review_pending`  VARCHAR(255)  -- 待审核字段列表（逗号分隔），就是显式的「未审核」tag
`review_flagged`  VARCHAR(255)  -- 最近一次因违规被改回默认值的字段
```

### `content_review_tasks` —— 审核队列

| 列 | 说明 |
|---|---|
| `user_id` / `field` | 谁、哪个字段（username / bio / avatar_url / ai_avatar_url / chat_background_url / diary_background_url） |
| `content` | 待审内容（文本原样，图片是 data URL，`MEDIUMTEXT`） |
| `is_image` | 图片任务走多模态消息体 |
| `status` | `pending` → `submitted` → `pass` / `reject`；请求失败标 `failed` |
| `batch_id` / `provider` | 属于哪个批次、走的哪条路（mimo-batch / inline / manual） |
| `reason` | AI 或管理员给出的理由 |

### `content_review_batches` —— 批次

一次提交一行，用来轮询状态和统计（`remote_id` 是上游批次 id，`output_file_id` 是结果文件）。

**老部署升级不用手动建表**：`ensureUserColumnsOnce()` 会在第一次访问时自动补列 + 建表
（后台打开「数据审核」页也会触发一次）。

## 六、部署

### 1. 部署代码

```bash
cd /tmp && rm -rf sp && mkdir sp && unzip -o /tmp/solace-deploy.zip -d sp
\cp -rf /tmp/sp/. /www/wwwroot/solace/
cd /www/wwwroot/solace && pm2 stop solace && rm -rf .next && npm run build && pm2 delete solace && pm2 start ecosystem.config.js
```

### 2. 在后台配置审核 AI

后台 →「数据审核」：

1. 填**接口地址**（`https://api.xiaomimimo.com/v1`）、**API Key**、**模型名**（`mimo-v2.6-flash`）
2. 点「**测试连接**」——通了才说明地址 / Key / 模型名都对
3. 点「**拉取模型**」选一个模型（或者直接手输）
4. 选**审核方式**：先用 `批量推理`，`自动降级` 保持开启
5. 按需设置**默认值**（至少设一下默认昵称）
6. **保存**

### 3. 配定时任务（关键）

审核是异步的，需要一个定时任务**收结果 + 交新活**。

**宝塔 → 计划任务 → Shell 脚本，每天 / 每 10 分钟一次**：

```bash
cd /www/wwwroot/solace && node scripts/review-submit.mjs >> logs/review.log 2>&1
```

⚠️ 建议 **10 分钟一次**：批量推理的结果延迟可能几分钟到几小时，
频率高一点用户体验更好（违规内容更快被处理掉）。

### 4. 顺手把日志也纳入轮转

`logs/review.log` 会一直增长，如果 `pm2-logrotate` 不管它，就加进宝塔的日志切割，
或者定期清（和 `cleanup.log` 一样处理）。

## 八、常见问题

## 自动定时提交（推荐方式）

**不用手动点「立即提交」** —— 应用启动后会注册一个定时器，
按你设置的间隔自动「收结果 + 交新任务」。

后台「数据审核」里有两个配置：

| 配置 | 说明 |
|---|---|
| **自动定时提交** | 总开关，默认 **开** |
| **自动提交间隔（分钟）** | 默认 **10 分钟**，范围 1-1440 |

**面板顶部会显示当前状态**：`自动提交：每 10 分钟` / `自动提交：已关闭（要手动点「立即提交」）`。

### 它是怎么工作的

```
第一次访问 /api/health 或后台审核页
     ↓
注册定时器（懒启动，之后一直在跑）
     ↓
每分钟"看一次表"
     ↓
距上次执行够久了（≥ 你设的间隔）？
     ↓ 是
① 收结果：查已提交的批次，完成的落库 + 处置违规内容
② 交新任务：把待审内容提交（先过本地词表，命中不浪费 AI）
```

**改完间隔不用重启** —— 下一次检查就会用新值。

### ⚠️ 「立即提交」的行为变了

它现在是**点完立刻返回**（提示"已开始提交"），实际工作在后台跑。
原因：降级成逐条时可能要一条条调一两分钟 AI，等着的话界面一直转圈，Nginx 还可能掐请求。

想马上看结果就点「**刷新**」。

### 也可以继续用宝塔计划任务

`scripts/review-submit.mjs` 仍然有效，两条路**可以同时存在**
（定时器会判断"距上次够不够久"，不会重复跑）：

```bash
cd /www/wwwroot/solace && node scripts/review-submit.mjs >> logs/review.log 2>&1
```

**建议**：用应用内的定时器就够了，脚本留着当备用。

### Q：点了「立即提交」，批次一直是「进行中」

批量推理**本来就是延迟返回的**，等几分钟再点「拉取结果」。
如果一直不动（超过一小时），点开批次看错误信息。

### Q：创建批次一直失败（HTTP 500 internal_error）

上游失败时**只回一句 internal_error**，看不出原因。用后台的「**测试批量接口**」诊断：

它会依次跑 ① 探活 → ② 上传文件 → ③ 用**四种参数组合**创建批次，
结果里还会带上**我们发出的 JSONL 原文**。

**那个 JSONL 原文可以直接贴到小米控制台的「批量推理 → 手动提交」页面做校验** ——
那里写着「系统将逐条校验，校验通过的成员可继续发送」：
**它校验不过 = 格式问题；它能过但你这边失败 = 账号 / 区域问题。**

按可能性排序：

| # | 原因 | 怎么确认 |
|---|---|---|
| 0 | ⚠️ **创建批次时少了 `name` 字段** | **这是本项目踩过的最大的坑**：官方文档的 curl 示例里**没有** `name`，但它**是必填的** —— 不传时上游直接回 500 internal_error，而且报错里完全看不出原因。<br>线索是从上游**真实返回**里看出来的：控制台建的任务在批次列表里带着 `"name":"test"`（对应页面上的「任务描述」）。<br>代码里现在已经带上 `name: "Solace 内容审核"` |
| 1 | **区域（region）不匹配** | 地址里的 region 段要和账号所在区域一致。不匹配时**探活能通、文件也能传，但一创建任务就 500** |
| 2 | **Key 是 Token Plan 的（`tp-` 开头）** | 批量**不支持 Token Plan 抵扣**，必须用 `sk-` 开头的按量计费 Key |
| 3 | **没实名认证 / 余额为 0** | 去控制台手动建一次任务就知道 |
| 4 | **JSONL 格式** | 照官方模板写：`{"custom_id":"...","method":"POST","url":"/v1/chat/completions","body":{"model":"...","messages":[...]}}` —— **`body` 里只放 `model` 和 `messages`**，别加 `max_tokens` / `temperature` 之类的额外字段（上游有「逐条校验」，照模板最稳） |
| 5 | ⚠️ **提交成功、但后台一直卡在「进行中」** | **查状态和下载结果时把地址用错了**。<br>批量一共**四个**调用：上传文件 / 创建批次 / **查状态** / **下载结果** —— 它们**全都必须走「批量推理接口地址」**（`batch-api-*.xiaomimimo.com`）。<br>曾经查状态和下载结果误用了「接口地址」（对话域名 `api.xiaomimimo.com`），请求打到对话服务上、永远查不到批次。表现就是「**控制台显示 5 分钟跑完了，后台一直显示进行中，点拉取结果也没反应**」。<br>代码里现在四处统一走批量地址 |

### Q：批量提交一直失败

**先检查「批量推理接口地址」有没有填。** 这是最容易漏的一步：

小米的批量推理用的是**独立域名**（`https://batch-api-{region}.xiaomimimo.com/v1`），
不是对话接口那个 `https://api.xiaomimimo.com/v1`，而且要去**控制台的「批量推理」页面**才能拿到。

另外还要满足：

- 模型必须是 `mimo-v2.6-pro` 或 `mimo-v2.6-flash`，**且模型名全小写**
- 账号要**完成实名认证**，并且**有现金余额** —— 批量推理只从余额扣费，**不支持 Token Plan 套餐抵扣**

**如果暂时不想折腾**：什么都不用管 —— 开着「自动降级」的话，程序已经自动改成逐条模式，
审核照样在跑，只是少了批量的五折价和闲时调度。

### Q：AI 返回的不是 JSON（或者读不懂）

**既不会被放过，也不会误伤** —— 这种情况会被标成 **`failed`（失败 · 待人工）**：

- **不会自动放过**：以前这里是「按合规处理」，结果一条明明是脏话的内容，
  因为模型没按格式回答就被判成通过了 —— 审核形同虚设。现在不会了。
- **也不会误伤**：不会去动用户的资料。
- **它只是变成「等你处理」**：后台点「**待人工**」筛选就能看到，
  点「查看内容」看原文，然后点**通过**或**驳回**。

如果你发现"读不懂"经常出现，说明**审核提示词要调** —— 把"只输出 JSON"的要求写得更强硬，
或者换个模型。

**顺便说明**：解析器已经做了大量兼容 —— 不同字段名（`verdict` / `result` / `label` /
`is_violation`）、布尔值、中英文取值（`合规` / `违规` / `pass` / `reject`）、
甚至 `"not violation"` 这类否定写法都能认出来。
所以走到 `failed`，说明模型确实没给出可判断的回答。

### Q：用户在被判违规之前又改了一次资料，会怎样

**不会误伤。** 处置前会先比对「被判违规的那份内容」和「用户当前的内容」：
不一致就只记录判定结果，**不动用户新改的内容**（任务状态会标成 `stale`）。

### Q：审核会花很多钱吗

- 文本任务（昵称 / 签名）很便宜，一次几十条也就几分钱
- 图片任务会贵一些（多模态）。**如果不放心，把「连图片一起送审」关掉**，
  图片就只进后台人工队列，零成本

### Q：怎么知道审核有没有在正常工作

- 后台「数据审核」页的状态卡片 + 批次记录
- `logs/review.log`（定时任务输出的）
- `content_review_batches.error` 里会记上游的原始报错

## 十、日记：情绪打标 + AI 生成（同一套批量队列）

⚠️ 这两件事**复用同一个队列**（`content_review_tasks`）和同一套批量 AI 配置，
只是任务类型不同 —— 靠 `task_kind` 区分：

| `task_kind` | 干什么 | 结果写到哪 | 小米控制台的批次名 |
|---|---|---|---|
| `review` | 内容审核（默认） | `users` 的对应列（违规就回填默认值） | `Solace·内容审核` |
| `diary_mood` | 日记情绪打标 | `diaries.mood` | `Solace·日记打标` |
| `diary_generate` | **AI 根据聊天记录生成日记** | 新建一行 `diaries`（`source='ai'`） | `Solace·日记生成` |

### 为什么合用一个队列

「立即提交」按钮、自动定时器、批次记录、结果回收 —— 这些**只写一套**。
一次提交会把三类任务一起送出去，但**按类型拆成不同批次** ——
这样小米控制台里三件事各自成行，出问题能一眼看出是哪一类。

### 情绪打标（diary_mood）

- **触发**：用户保存日记时自动入队（`app/api/user/diaries/route.js`）
- **提示词**：后台「日记」页 → 打标提示词
- **解析用白名单**：模型输出的词必须在 8 个情绪词里才采纳；挑不出来就落到「默认情绪标签」
- 用户自己选的标签存在 `user_mood`，**和 AI 的 `mood` 分开存、前端两个都显示**（标着「用户 ·」/「AI ·」）
- 改了日记正文 → **清掉旧的 AI 标签并重新入队**（用户标签不受影响）

### AI 生成日记（diary_generate）

- **触发**：定时器**每天一次**（后台「日记」页 → 每日生成时间，默认 23 点），为「**昨天**」生成
  - 为什么是昨天：今天还没聊完，生成出来是半截的
- **也支持手动补跑**：后台「日记」页 →「① 立刻为昨天排生成任务」
- **跳过条件**：
  - 昨天消息数 < 最少条数（聊得太少，硬凑出来的日记没意义）
  - **队列里同一天已经有活跃任务** —— 去重键是 `diary_generate:{userId}:{日期}`
  - `diaries` 里已经有那一天的 AI 日记（按 `diary_date` 精确判断）
- **输入**：昨天的聊天记录（最多 N 条、总长 ≤ N 字，超出从**末尾**截 —— 那儿情绪最完整）
- **⚠️ 输出格式是「行首标记」而不是 JSON**：
  ```
  标签：轻快
  标题：今天有点不一样
  正文：
  今天……
  ```
  让模型在批量里吐 JSON 太容易坏（审核那边踩过），这个格式容错好得多。
- **解析失败 → 标 `failed` 交人工**，绝不瞎写一篇塞给用户
- 写入时带两个关键字段：
  - `source = 'ai'` → 前端标上「AI 生成」
  - `diary_date = 昨天`（**不是生成时刻** —— 否则用户会以为是今天的日记）

### ⚠️ 去重规则（改队列相关代码前先读）

**同一份内容在队列里只应该有一条活跃任务。** 每条任务入队时都会算一个 `dedupe_key`：

| 任务 | 去重键 | 为什么这样设计 |
|---|---|---|
| 内容审核 | `review:{userId}:{字段}:{内容指纹}` | 同一份内容不重复送审 |
| 日记打标 | `diary_mood:{diaryId}:{内容指纹}` | **改了正文指纹就变**，所以"改完重新打标"不受影响 |
| 生成日记 | `diary_generate:{userId}:{日期}` | ⚠️ **刻意不用内容指纹** —— 它的输入是那天的聊天记录，而聊天记录会**一直变长**，用指纹的话每多聊一句就换一个 key，去重等于没做 |

入队前查同 key 的**活跃任务**（`pending` / `submitted` / `manual`），有就跳过。
**跑完的不算活跃** —— 失败了要允许重来。

**出过的事**：这道去重以前只存在于"排生成任务"那里，而且**只查 `diaries` 表**
（看"24 小时内是否生成过"）—— 上一次生成**失败**时那儿根本没记录，等于没去重；
`enqueueReview` 那边更是从来不查重。于是「**重试失败任务**」（把旧的 failed 打回队列）
+「**再排一次**」= **两条任务 → 两篇一模一样的日记**。

现在三道防线：

```
① enqueueReview 入队前查 dedupe_key      ← 源头
② createDailyDiaryTasks 排任务时查队列    ← 中间
③ applyVerdict 真正写 diaries 前再查一次  ← 兜底
```

### 后台在哪看

| 想看 | 去哪 |
|---|---|
| 两类任务的状态统计 | 后台「**日记**」页（打标 / 生成**分成两个列表**，各有四个数字） |
| 任务原文（日记正文 / 聊天记录） | 同页 →「看原文」 |
| 批次记录（含失败原因） | 后台「**数据审核**」页 → 批次记录 |

### 常用排障

| 现象 | 原因 / 怎么办 |
|---|---|
| 打标一直「待提交」 | 没点「立即提交」，或自动定时器没起来（访问一次 `/api/health` 就会启动） |
| 生成任务排了但没日记 | 去「数据审核」页点「立即提交」，再等几分钟点「拉取结果」 |
| 生成出来格式乱 | 模型没按约定输出 → 任务会标 `failed`，去「看原文」看它的原始返回 |
| 生成结果**为空**（原因里只有一个空冒号） | 曾经是因为**批量请求没带 `max_tokens`**，长输出被上游默认额度截断。现在按任务类型给了额度（生成日记 3000），并且错误信息里会带 `finish_reason` —— 看到 **`finish_reason=length`** 就是又被截断了：把后台的额度调大、或者把生成日记的提示词要求写短一点 |
| **日记写到一半戛然而止**，但任务显示"**已完成**" | `finish_reason=length` —— 被 `max_tokens` 掐断了，而**半截内容照样符合「标签/标题/正文」的格式**，所以解析成功、任务被标成了 `pass`。现在**截断的结果一律标 `failed` 不保存**（半截的日记比没有更糟）；同时把输入压短了（条数 60 / 2500 字）、输出额度提到 3000 |
| 失败的任务一直不重跑 | **会自动重试**（最多 2 次，见 `lib/content-review.js` 的 `takePending`）。到顶之后去后台「**日记**」页点「**重试失败任务**」—— 它会把失败任务打回队列并清零重试计数 |
| 想调生成风格 | 后台「日记」页改「生成日记提示词」；⚠️ **改格式的话代码里的解析也要跟着改**（`lib/content-review.js` 的 `parseDiaryDraft`） |
| 用户说"我没写过这篇日记" | 查那篇的 `source` 是不是 `ai`，以及 `diary_date` 是不是前一天 |
