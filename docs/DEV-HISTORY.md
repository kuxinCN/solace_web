## 阶段一｜技术选型的转折：从 Supabase 到自建 MySQL

**背景**
项目最初用户端数据放在 Supabase（BaaS），前端直接调它的 SDK。

**关键问题**
- 数据落在第三方平台，后台管理、用户数据查看都要绕一层；
- 需要自己实现的部分（账号体系、密码找回、管理员权限）在 Supabase 上反而更别扭；
- 竞赛场景下，评委更希望看到"自己搭的后端"，而不是托管服务。

**决定**
全部迁到自建 MySQL，删掉 `@supabase/supabase-js`，所有数据读写走自己的 REST 接口。

**收获**
- 对"后端到底做了什么"有了完整认知：连接池、会话、事务、索引、迁移；
- 后来遇到问题（500、502、连不上库）都能自己定位，而不是"黑盒依赖"。

## 阶段二｜后端从零搭建

**做了什么**

| 模块 | 内容 |
|---|---|
| 数据库 | 10 张表（管理员、会话、配置、审计、验证码、用户、用户会话、对话、消息、日记），全部预处理语句 |
| 认证 | 用户端：邮箱验证码 + 账号密码并存；管理端：bcrypt 密码 + TOTP 动态验证码双因素 |
| AI | 对话补全（支持流式 SSE）、文字转语音（两种协议） |
| 后台 | 配置管理、用户管理、用户数据查看、审计日志 |
| 兼容 | 老部署升级时自动补列（`ensureUserColumnsOnce`），不用手工改表 |

**关键问题与解法**

1. **`SHOW` 语句在某些 MySQL 上报 1295** → 改用查 `information_schema`；
2. **图片不落磁盘** → 压缩成 base64 存 `MEDIUMTEXT`，于是头像字段必须扩容，
   于是又有了"自动检测并 `MODIFY COLUMN`"的升级逻辑；
3. **密码要不要可逆** → 业务要求"后台能查看用户密码"，最终用 AES-256-GCM 可逆加密，
   并把安全权衡写进部署文档（这是产品需求与安全原则的取舍，不是疏忽）。

**收获**
"自动补列"这个设计后来救了多次 —— 只要新加了字段，老库访问一次就自动升级，
不用写迁移脚本、不用停机。

## 阶段三｜上线部署踩过的坑（最有素材价值的一段）

### 1. 域名解析与 CDN

- 一开始两个域名一个直连、一个走了腾讯云 EdgeOne CDN；
- **发现**：CDN 对动态站点帮助有限，且跨境回源反而更慢；
- **结论**：演示场景优先直连；静态资源才值得走 CDN。

### 2. HTTPS 证书错配

- 现象：访问 A 域名，返回的却是 B 域名的证书 → 浏览器报"不安全"；
- **根因**：Nginx 只有一个 HTTPS 站点，其他域名的 443 请求被它接管；
- **解法**：给每个域名单独申请证书、单独建站点；
- **副产品**：搞清了 `openssl s_client -servername` 这个排查证书的利器。

### 3. 移动端"点了没反应"

- 现象：iPhone + Safari + 移动网络，登录页页签点不动；换浏览器、换网络都正常；
- **排除过程**：桌面无痕正常 → 排除缓存；同网络其他浏览器正常 → 排除网络；
- **结论**：CN2 线路对移动不友好 + 首屏 JS 跨境加载慢 → hydration 未完成 → 按钮点不动；
- **解法**：gzip、BBR、静态资源走 CDN，前端页面把触摸目标做大并加 `touch-manipulation`。

**收获**
排障最有效的手段永远是**二分法**：把变量一个个固定住，剩下的那个就是原因。

### 4. 「域名 500、IP 正常」—— 两个实例

- 现象反复出现：域名 502/500，但 `127.0.0.1:3000` 正常；
- **根因**：pm2 起了一个实例（3000），宝塔「Node 项目」又起了一个（3001），
  Nginx 指向了那个"在构建产物残缺时启动、之后没重启过"的旧进程；
- **解法**：只保留一个实例；构建后**所有**跑着旧产物的进程都要重启。

### 5. MySQL 被 OOM 杀掉

- 现象：所有请求先卡十几秒再 500；
- **关键判断**：代码错误是**秒返回**，卡住说明是**外部依赖超时**；
- **根因**：`npm run build` 吃满内存（1.9G），系统杀掉了 MySQL；
- **解法**：加 2G swap；构建前先 `pm2 stop`。

**收获**
这类"看起来是代码问题、其实是资源问题"的故障，用日志和 `systemctl status` 几分钟就能定位 ——
前提是**知道该看哪里**。

## 阶段四｜工程加固（四项优化）

| 方向 | 做了什么 |
|---|---|
| **稳定性** | 健康检查接口 `/api/health`、数据库备份脚本（含恢复步骤）、运维手册、日志轮转 |
| **安全** | 错误信息默认脱敏（详情只进日志）、补齐各写接口限流、上传按**文件头魔数**校验真实格式 |
| **体验** | 后台可改 AI 提示词（保存即生效）、对话标题自动生成、日记情绪标签 |
| **材料** | 后台数据看板（零依赖纯 CSS 柱状图）、完整 API 文档、压测脚本 |

**几个值得写进报告的设计决定**

1. **健康检查不含任何敏感信息**，所以可以安全地暴露给外部监控；
2. **错误脱敏**：已知错误码翻译成人话，未知错误只回一句通用提示，原始报错进服务端日志 ——
   因为 MySQL 的原始报错常常带表名和用户数据（`Duplicate entry 'xxx@qq.com' for key ...`）；
3. **情绪标签刻意不做评分**：只有 8 个温和的描述词，不做数值、不做趋势、不用红黄绿配色，
   因为产品定位是"陪伴"而不是"给用户的情绪打分"。

## 阶段五｜前后端融合

**背景**
前端同学在自己那份项目上继续开发（新增了 TTS 语音、图片裁剪、忘记密码等），
后端在我们这边；两边各有更新，需要合并成一份。

**做法**

1. 先做**逐文件对比**（目录结构、文件行数、API 调用清单），列出"谁更新"；
2. 按**功能归属**决定取舍，而不是整目录覆盖：
   - 用户端界面 → 用前端的（TTS、裁剪、忘记密码）
   - 管理后台 → 用我们的（数据看板、日志面板）
   - `lib/`、`app/api/` → 用我们的（安全加固、限流、新接口）
3. **补齐前端需要但后端缺失的能力**：
   - `/api/auth/send-reset-code`、`/api/auth/reset-password`（忘记密码）
   - `mailer.js` 支持自定义验证码有效期/冷却/邮件文案
   - `conversations.last_message_at`（会话列表按最后消息时间排序）

**过程中的教训**

- 融合时最容易出的问题**不是逻辑冲突，而是"漏传文件"和"漏装依赖"**；
- `npm run build` 报 `webpack errors` 时，真正的原因在上面几行 ——
  `npm run build 2>&1 | grep -A4 "Can't resolve"` 能直接看到缺哪个模块；
- 构建成功 ≠ 功能正常（详见 `INCIDENTS.md` 的 INC-001）。

## 阶段七｜背景音乐：三种音源与一次错误的自我推翻

**背景**
要加"进站后播放背景音乐"。网易云是绕不开的音源，但它的可用性一直是个坑。

**做了什么**

| 音源 | 实现 | 能力 |
|---|---|---|
| **本地上传 / 外链直链** | `<audio>`，服务端 `/api/music/file?name=` 代理 | 能自动播放、能切歌 |
| **网易云收藏** | **官方外链播放器 iframe** | 不能自动播放、不能切歌（受官方限制） |

**关键决定：网易云只存 ID，不做播放地址解析。**

一开始的冲动是"抓一下真实播放地址不就能自己播了吗"。但没有做，理由三条：
不越界（官方不允许解析）、不稳定（对方一改就废）、不值得（一个 iframe 就能用）。
所以数据库里只存 `song.id` / `playlist.id`，前端拼官方外链。

**踩的坑（三个叠在一起，排查了好久）**

「点了没动静」看起来是一个问题，实际是三个：

1. **宝塔 Nginx 的静态后缀规则**把 `?name=xxx.mp3` 这种请求拦掉了 → 新增 `/api/music/file?name=` 走应用层读取；
2. **`index` 越界**：歌单里只有 3 首，但记住了上次播第 5 首 → 加 `safeIndex`；
3. **歌单里根本没有本地歌 / 音源没切** —— 这个是"配置问题"，不是 bug。

**⚠️ 一次被用户纠正的错误判断**

我一度认定"网易云外链在手机浏览器上不支持"，并据此写了"按屏幕宽度强制降级到本地"的逻辑。
用户给了一个反例（手机上能正常播）。**结论是我错了**：那是当时那台设备/网络的问题，
不是平台限制。那条按宽度降级的逻辑已经撤掉，改成只在**真实网络请求失败**时才降级。

> 教训：**不要把自己的复现失败当成平台的能力边界**。判断"某个服务不支持某场景"之前，
> 至少要有一个明确的技术原因，否则就是在猜。

**另一个反直觉的 bug：收起浮窗，音乐停了**

「关闭背景音乐」按钮调的是 `pause()` —— 用户以为"关闭"是关掉那个面板，代码理解成了关掉音乐。
改成「收起浮窗（音乐继续）」，并把 iframe 面板**始终挂载**（收起时挪到屏幕外 + `opacity: 0`），
这样重新展开时不用重新加载、播放进度也不丢。

**音频为什么不入库**
试过存 base64 进 MySQL，很快放弃了：单条音频 4MB 会撞上 `max_allowed_packet`，
而且连接池只有 5 个连接，一个用户存音频就能把池子占满。
最后改成**音乐包导出/导入 + 备份脚本带上 `music` 目录**。

## 阶段八｜内容审核：一次完整的异步系统设计

**背景**
用户能填的公开内容（昵称、签名、头像、AI 头像、聊天背景、我的页背景）需要审核。
但"每次改资料都同步调一次 AI"有三个问题：慢（用户要等）、贵（改一次调一次）、
脆（AI 挂了资料就改不了）。

**⭐ 最终设计：异步 + 批量**

```
用户改资料
   ↓
立刻生效 + 打「未审核」标记 + 进队列     ← 用户无感，不等待
   ↓
攒一批 → 提交给小米批量推理（五折价）
   ↓
定时轮询回收 → 合规就清标记 / 违规就回填默认值
```

**⚠️ 批量推理踩的四个坑（每个都卡了很久）**

| # | 现象 | 根因 |
|---|---|---|
| 1 | 批次一直「进行中」，18 小时不动 | **查状态 / 下载结果误用了对话地址** → 必须走 `batchBaseUrl`。四个调用（上传 / 创建 / 查状态 / 下载）**一个都不能少** |
| 2 | 创建批次一直 500 `internal_error` | **少了 `name` 字段** —— ⚠️ **官方文档里根本没写这个字段**，是从控制台的返回体里发现的 |
| 3 | 改 `completion_window` 就 500 | 上游只认 `24h` → 加了"失败自动退回 24h 重试" |
| 4 | 整批创建失败 | **图片不能进批量** —— 多模态消息体会让整批挂掉 → 图片单独分流（人工队列 / 逐条审） |

**⭐ 一条不肯妥协的设计：解析读不懂，绝不默认放行**

最早的实现里，AI 返回格式不对时会"按通过处理"。这个默认值方向是**错的** ——
审核这种东西，读不懂就该让人看一眼，而不是放过去。改成了三态：

```
明确 pass  → 清标记
明确 reject → 回填默认值
读不懂     → 标 failed，交人工
```

**⭐ 词表：从"关键词"到"家族 + 变体"**

第一版词表只有规范写法，结果「我tm草泥马，你个废物，臭sb」整句一个都没命中。
重做时按两个维度铺开：

- **家族**：草泥马 / 草泥馬 / 卧槽 / 我操…（同一个词的各种写法）
- **拼音缩写**：`sb` / `tm` / `tmd` / `nmsl` / `cnm` / `mdzz` / `wdnmd` —— ⚠️ 这几个必须用**词边界**匹配，
  否则 `sb` 会命中 `absorb`、`tm` 会命中 `atm`

**⭐ 一个 Next.js 的坑：定时器不能用 `instrumentation.js`**

给审核加自动定时提交，最自然的做法是 `instrumentation.js`。但它**让整个 build 失败**：

```
instrumentation → scheduler → settings → db → node:path
                                              ↑ edge 环境没有这个模块
```

Next 14 会为 **server 和 edge 各编译一次** `instrumentation`，webpack 顺着依赖链
一路静态解析到 `node:path`，edge 环境直接报错。

**解法**：改成**懒启动** —— 第一个访问 `/api/health` 或后台审核页的请求调用
`startReviewScheduler()`（幂等）。不用改任何 Next 配置，也不影响冷启动。

**⭐ 顺手做对的一件事：按任务类型拆批次**

一开始所有任务混成一个批次，名字统一叫「Solace 内容审核」。
后来日记打标、AI 生成日记也进了同一个队列 —— 在小米控制台里看到一排同名任务根本分不清谁是谁。
改成**按类型拆批次**，各自有名字（`Solace·内容审核` / `Solace·日记打标` / `Solace·日记生成`），
副作用还都是好的：某一类失败不再拖累另一类。

## 阶段九｜日记：把"AI 的"和"我的"分清楚

**背景**
日记原本只有 AI 打的一个情绪标签。后来加了两件事：用户自己也能选心情，
以及 **AI 根据聊天记录替用户写日记**。

**⭐ 核心设计：两个标签并存，绝不互相覆盖**

| 字段 | 谁写的 | 前端显示 |
|---|---|---|
| `diaries.user_mood` | **用户自己选的** | `用户 · 轻快` |
| `diaries.mood` | **AI 读出来的** | `AI · 平静` |

用户改正文 → **清掉 AI 的旧标签并重新入队**（用户选的标签不动）。

**⭐ AI 生成日记：三个决定**

1. **只生成"昨天"的** —— 今天还没聊完，生成出来是半截的；
2. **输入格式用「行首标记」而不是 JSON**：
   ```
   标签：轻快
   标题：今天有点不一样
   正文：
   今天……
   ```
   让模型在批量推理里吐 JSON 太容易坏了（审核那边已经吃过一次亏）。
   用"行首标记 + 后面全是正文"，容错性好得多；解析不出来就标 `failed` 交人工，
   **绝不瞎写一篇塞给用户**。
3. **`diary_date` 和 `created_at` 分开** —— 这篇日记写的是"昨天"，但生成时刻是"今天 23 点"。
   只看 `created_at` 的话用户会以为是今天的日记。所以列表和详情**一律以 `diary_date` 为准**。

**⭐ 一个必须标注的东西**

生成的日记在前端会带一个「**AI 生成 · 09/22**」徽章。
不是为了免责，是因为**用户得知道这不是自己写的** —— 否则会产生"我什么时候写过这个？"
的困惑，甚至以为账号被盗。

## 阶段十｜性能：两个反直觉的故障

### 1. 后台概览页要 600-700ms

**根因**：`users JOIN messages GROUP BY` —— 先 JOIN 再聚合，等于把消息表整个拉出来再分组。
**改法**：「先聚合再 JOIN」，并加了 `messages(created_at, user_id)` 复合索引。
**收获**：SQL 的执行顺序比"写得优雅"重要得多。

### 2. PM2 重启了 208 次

**现象**：服务隔一阵就重启一次，日志里没有报错。
**根因**：Node 的 V8 堆上限（约 1.8G）和 PM2 的 `max_memory_restart: 600M` 不匹配 ——
程序还没到 V8 的上限，PM2 先认为"它吃太多了"把它杀了。
**改法**：`node_args: "--max-old-space-size=450"` + `max_memory_restart: 700M`，两个数字**对齐**。
**收获**：这两个值必须一起设，只设一个就是定时炸弹。

## 阶段十一｜压力评估：从"事后审核"到"实时接住"

**背景**
前面的内容审核、日记打标都是**异步批量**的（提交后等几分钟）。压力评估不行 ——
它要在用户发完一条消息之后就能判断。

**⭐ 四层漏斗（九成以上的消息不花任何 Token）**

```
① 本地词表打分（每条消息，0 Token，<20ms）
② EMA 平滑 + 聊天 / 日记双通道融合
③ 触发判断：每 10 条 · 命中关键词（2 分钟冷却）· 危机词
④ 只有触发时才调一次 AI（输出 30 token 的极简 JSON）
```

**⭐ 于是项目里有了两条并行的 AI 通道**

| | 内容审核 / 日记打标 | 压力评估 |
|---|---|---|
| 时机 | **异步**，等几分钟没关系 | **实时**，发完消息就要判断 |
| 接口 | 小米**批量推理**（五折价） | **对话接口**（批量来不及） |
| 目的 | 合规 / 归档 | 及时接住用户 |

**⭐ 三个不肯妥协的地方**

1. **危机词用带上下文的正则，不用 `includes()`** —— 中文没有词边界，
   `includes("消失")` 会把「我的焦虑**消失**了」判成危机（那是好转！）；
   `includes("死")` 更是会命中「笑死我了」。
2. **不诊断** —— 界面上给的是"情绪档位"（「有点累」），不是"你有焦虑倾向"。
   档位的措辞**后台可配**，就是怕写死在代码里没人管语气。
3. **用户点「先不用」→ 阈值真的 +5** —— 拒绝不能只是视觉上消失。
   用户说"不用"之后，系统必须真的变得更含蓄。

**⭐ 复用而不是重写**

"3 分钟呼吸放松"这个页面**项目里早就有了**（`FirstAid.jsx`，在「治愈小屋」里，
还带蝴蝶拍和心理援助热线）。所以只给它加了两个可选 prop，让弹窗能"直接进某个方式"——
**不传时行为和以前完全一样**，治愈小屋里三种方式仍然常驻。

**⭐ 顺手做的一件事：把规格修订记录下来**

这个功能有一份外部给的原始规格文档。落地时改动了 5 处（危机词匹配方式、时区计算、
日记衰减参数恒为 0、极端句排序有正确性 bug、高频写库），另外加了 5 项要求。
这些都记进了 `docs/STRESS-DESIGN.md` 开头的「落地修订」表，**原规格保留原样**。

> 这比"直接改掉"有价值：评审时能看出哪些是原设计、哪些是按实际情况调整的，以及**为什么调**。
