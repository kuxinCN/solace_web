## 维护约定

> ⚠️ **完整版在根目录的 [AGENTS.md](../AGENTS.md)** —— 那里还有红线清单、常用命令、
> 以及这个项目特有的坑。这里只列和文档相关的部分。

### 每次改完代码都要做

1. **更新 [CHANGELOG.md](../CHANGELOG.md)**
   - **大更新**（新功能 / 架构调整 / 破坏性变更）→ 顶部新增一节，说清
     「**为什么做**」「用户能看到什么变化」「要注意什么」
   - **小更新**（修 bug / 小优化）→ 写进对应版本的 `### 修复`，
     格式是 **现象 → 根因 → 修复**
   - ⚠️ **日期怎么算**：**0 点前后（约 0:00 – 5:00）完成的更新和变动，
     一律记进前一天的日志**，算同一批 ——
     那个时段的工作几乎都是前一天那批的延续（熬夜接着做），
     按自然日切开会把"同一批改动"劈成两次更新，看日志的人会以为是两件事。
     判断依据是"**从什么时候开始做的**"，不是"什么时候写完的"
2. **大更新还要回头更新 [README.md](../README.md)** ——
   至少同步**功能一览**（用户端 / 管理后台）、**AI 能力配置**、**项目结构**、**文档索引**
3. **线上事故，或排查超过半小时的 bug** → **额外**补进 [INCIDENTS.md](./INCIDENTS.md)，
   按那边的模板写（现象 / 根因 / 修复 / 预防）

> 为什么分两处：**更新日志是给"想知道变了什么"的人看的**，
> **事故记录是给"下次别再踩"的人看的**。

### 按改动类型找对应文档（**主动对照，别等人提醒**）

| 改了什么 | 更新哪份 |

### ⚠️ 和某个功能**深度绑定**的文档，动了那个功能就得改它

有些文档是**某个功能专属**的 —— 只要碰了那个功能就得改它，
**哪怕改动看起来很小**（改个参数默认值、调个阈值、换个措辞都算）：

| 动了什么功能 | 必须同步 |
|---|---|
| **背景音乐 / 网易云 / 音源 / 播放器 UI** | `MUSIC.md` |
| **压力评估 / 放松提醒 / 危机干预** | `STRESS-DESIGN.md` + `STRESS-SPEC.md` |
| **内容审核 / 日记打标 / AI 生成日记** | `CONTENT-REVIEW.md` |
| **性能 / 索引 / PM2 / 缓存 / 慢查询** | `PERFORMANCE.md` |
| **数据库结构 / 备份 / 恢复 / 巡检** | `OPERATIONS.md` |
| **登录 / 会话 / 限流 / 上传校验 / 密码加密** | 根 `README.md` 的「安全设计」那一节 |

> ⚠️ **功能专属文档最容易过期** —— 它不在"每次都会翻"的路径上，
> 平时没人看，等真要查的时候才发现写的是三个版本前的行为，**比没有文档更误导人**。
>
> **判断方法**：改完之后问自己一句 ——
> **"如果这份文档里写的还是旧行为，会不会把人带偏？"** 会，就顺手更新。

## 几个关键约定（新人先看这里）

| 约定 | 说明 |
|---|---|
| **应用端口** | 统一 **3000**（`ecosystem.config.js` 里写死），Nginx 反代必须指向它 |
| **只保留一个实例** | 要么用 pm2，要么用宝塔 Node 项目，**不要两个都跑** —— 否则会出现"改了代码一半生效"或 502 |
| **构建后必须重启** | `npm run build` 只是生成 `.next`，运行中的进程还加载着旧代码 |
| **内存小就先停应用再构建** | `pm2 stop solace` → `npm run build` → `pm2 start solace` |
| **配置不进版本库** | `.env.local`、`config/db.json`、`config/installed.lock` 都不要上传/外发 |
