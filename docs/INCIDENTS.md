## INC-001｜日记页数据"消失"：引用了不存在的导出函数

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-20 |
| **发现方式** | 用户在日记页刷新后发现列表为空；但后台能看到全部日记 |
| **严重程度** | **高** |
| **是否丢数据** | **否** —— 数据一直完好，只是接口 500 导致前端渲染不出来 |

### 现象

1. 首页、聊天页均正常，**只有日记页刷新后列表为空**；
2. 情绪标签从来不出现；
3. 后台「用户数据 → 日记」能看到全部日记 —— 说明数据在库里好好的。

### 根因

`app/api/user/diaries/route.js` 与 `app/api/user/diaries/mood/route.js` 里写的是：

```js
import { ensureDiaryColumnsOnce } from "@/lib/schema";
```

但 `lib/schema.js` **从未导出过 `ensureDiaryColumnsOnce`**。它实际导出的是：

- `ensureDiaryColumns()` —— 没有 `Once` 后缀
- `ensureUserColumnsOnce()` —— 内部已经包含 diaries 的补列

于是运行到这一行时抛 `TypeError: ensureDiaryColumnsOnce is not a function`，
接口直接返回 500，前端拿不到日记列表。

### 为什么构建没拦住

`next build` 遇到"导入了不存在的命名导出"时通常**只给警告**，把它当成 `undefined` 放过去，
**构建照常成功**。只有真正请求那个接口才会崩 —— 典型的 **"构建通过 ≠ 功能正常"**。

### 修复

两处 import 与调用统一改为 `ensureUserColumnsOnce()`。同时做了两项加固：

1. **补列失败不再拖垮主流程** —— `ensureUserColumnsOnce()` 在 diaries / conversations / messages
   等接口里都用 `try/catch` 包住：即使补列失败（例如数据库账号没有 `ALTER` 权限），
   用户依然能看到自己的数据；
2. 前端 `requestDiaryMood` 的失败分支加了一行 `console.warn`（对用户仍然静默），
   便于现场排查。

### 预防措施（已纳入流程）

1. **新增跨模块引用后，必须实际请求一次那个接口** —— 不能只以"build 成功"为准；
2. "某个功能突然不可用、但其他都正常"时，**第一件事看服务端日志**：
   `TypeError` / `is not a function` 会直接打在那里；
3. 涉及"升级兼容"的自动补列 / 自动修复逻辑，**一律用 `try/catch` 包住**，
   不允许影响主流程；
4. 协作场景下，**同一份代码分发给别人之前，先自测关键路径**（日记列表与新增、发消息、登录），
   避免把缺陷扩散出去。

### 相关文件

- `app/api/user/diaries/route.js`
- `app/api/user/diaries/mood/route.js`
- `lib/schema.js`
- `app/chat/page.js`

## INC-002｜域名 502 / 应用 500：同一项目跑了两个实例

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-19 ~ 09-20 |
| **严重程度** | **高**（反复出现多次） |
| **是否丢数据** | 否 |

### 现象

- 用域名访问报 `502 Bad Gateway`（Nginx），或页面只有一句 `Internal Server Error`；
- 但 `http://127.0.0.1:3000` 或 IP 直连却是正常的；
- 改了代码后页面没变化，"一半生效一半不生效"。

### 根因

服务器上**同时跑了两个实例**：

| 端口 | 谁启动的 |
|---|---|
| 3000 | pm2（`ecosystem.config.js`） |
| 3001 | 宝塔「Node 项目」 |

Nginx 的 `proxy_pass` 指向了其中一个，而那个恰好是**在构建产物残缺时启动、之后没重启过**的旧进程。

叠加的另一个因素：`rm -rf .next` 之后 `npm run build` 没有成功（内存不足被系统杀掉），
`.next` 处于残缺状态，进程启动时直接报：

```
Could not find a production build in the '.next' directory.
```

### 修复

1. 只保留一个实例：停掉宝塔的 Node 项目（**只停别删**，删除可能连站点配置一起删掉），
   或反过来 `pm2 delete solace`；
2. Nginx 的 `proxy_pass` 指向正在跑的那个端口；
3. `rm -rf .next` → `npm run build`（确认**退出码 0**；只看 `✓ Compiled successfully` 会被 lint 骗过去）→ `pm2 start`；
4. 加 2G swap，避免构建时内存不足被 OOM 杀掉。

### 预防措施

- **只保留一个实例**，随时用 `ss -lntp | grep -E ':3000|:3001'` 确认；
- **构建前后**：先 `npm run build`，构建成功后再 `pm2 delete solace && pm2 start ecosystem.config.js`
  （⚠️ 本条原来写的是"先 `pm2 stop` 再 build"，**已被 INC-014 修正**：停服务的步骤必须排最后；
  只有内存不足时才先停，且把 `stop → build → start` 整段交给脚本 / `nohup`，不要手敲 `&&` 链）；
- **构建产物更新后，所有跑着旧产物的进程都必须重启**。

## INC-003｜MySQL 被系统杀掉，导致全站卡住后 500

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-20 |
| **严重程度** | **高** |
| **是否丢数据** | 否 |

### 现象

- 所有请求先**卡住很久**（十几秒），然后返回 500；
- `curl http://127.0.0.1:3000/api/health` 也是长时间无响应后 500；
- 与"代码写错"的区别很明显：**代码错误是秒返回**。

### 根因

`systemctl status mysqld` 显示 `inactive (dead)` —— MySQL 被停了。
时间点与 `npm run build` 高度吻合：**构建占满内存，内存不足时系统杀掉了 MySQL 进程**。

应用侧表现出的"卡住"，是在等数据库连接超时（`connectTimeout: 8000`）。

### 修复

```bash
systemctl start mysqld
systemctl enable mysqld      # 顺带打开开机自启
pm2 restart solace           # 让应用重建数据库连接
curl -s https://你的域名/api/health
```

### 预防措施

1. 内存小的服务器**先加 2G swap**；
2. **构建前先 `pm2 stop solace`**，把内存让给构建
   （⚠️ **顺序已由 INC-014 修正**：先 build、最后才停 / 切服务；只有内存不足时才先停，
   且把 `stop → build → start` 整段交给脚本 / `nohup`，别手敲 `&&` 链）；
3. 打开 MySQL 的开机自启；
4. 接一个外部监控探针指向 `/api/health`，挂了能第一时间收到提醒。

## INC-004｜AI 回应错位：日记写"开心"，它却回"我读到你很累"

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-20 |
| **发现方式** | 用户在日记里写"我好开心"，让 AI 读，AI 回"读到了你很累" |
| **严重程度** | **中**（不影响数据，但严重损伤体验 —— 用户会觉得"AI 根本没在听我说话"） |
| **是否丢数据** | 否 |

### 现象

日记正文与 AI 的回应**牛头不对马嘴**：内容明显是正向的，AI 却按"用户情绪低落"来安慰。

### 根因

**给 AI 的指令里写了具体的情绪示例**，模型会直接照抄那个示例的情绪，而不是去读用户真正写了什么。

前端「读日记」的指令原文（`app/chat/page.js` 的 `DIARY_INSTRUCTION`）：

```
你刚刚读了用户的日记，请以陪伴者身份自然地回应。
可以自然引用日记里的具体细节或情绪（比如"你提到今天很累""你写的那段话我记下了"），
然后给予一定安慰，并向用户表示如果可以继续倾诉。
```

两个问题叠在一起：

1. **示例本身是一个负面情绪** —— "你提到今天很累"被当成模板套用；
2. **"然后给予一定安慰"** —— 这句话预设了"用户状态不好"，等于要求 AI 先假设用户难过。

同样的示例也出现在另两处：

- `app/chat/page.js` 的 `SYSTEM_PROMPT`（前端兜底人设）；
- `lib/settings.js` 的 `ai.systemPrompt`（后台默认提示词）。

### 为什么不是后端的问题

链路是通的，逐段验证过：

| 环节 | 实际内容 |
|---|---|
| 前端调用 | `diaryContext: diary.content` —— 传的确实是当前这篇日记的正文 |
| 前端消息构造 | 用户消息里只放标题，正文单独走 `diaryContext` 字段（设计正确） |
| 后端 `/api/chat` | 按 `diaryPrompt` 模板把正文注入成 system 消息（正确） |

所以数据一路是对的，**是最后一步"怎么跟模型说话"出了问题**。

### 修复

三处统一改成：**不给情绪示例，改为要求模型先判断真实情绪**。

```
1. 用户倾诉时，你的第一句话必须先回应他的感受，让他觉得被听见。
   不要预设他的情绪是负面的 —— 他分享开心的事就一起高兴，难过的时候才轻轻接住。
```

读日记的指令也改成：

```
先读懂日记里真实的情绪：是开心的就一起高兴，是低落的才给予安慰，不要预设用户状态不好。
```

> ⚠️ **注意**：提示词存在数据库里，改 `lib/settings.js` 的默认值**不会影响已经存在的配置**。
> 所以线上还需要在后台「对话 AI」页面手动改一遍第 1 条。

### 教训（写 AI 指令时的通用原则）

1. **不要给具体情绪的示例** —— 模型对示例的模仿远强于对规则的遵守。想要它"随机应变"，
   就要写"先判断真实情绪"，而不是举例让它套；
2. **警惕预设性措辞** —— "给予安慰""安抚他"这类词本身就暗示了用户的情绪方向；
3. **改提示词后要回归测试** —— 至少用"正向内容"和"负向内容"各测一次，确认两种都能正确回应；
4. 提示词存在数据库时，**代码里的默认值只是给新装用的**，线上一律以后台配置为准。

### 相关文件

- `app/chat/page.js`（`DIARY_INSTRUCTION` / `SYSTEM_PROMPT`）
- `lib/settings.js`（`ai.systemPrompt` 默认值）
- 后台「对话 AI」页面的线上配置（需手动同步）

## INC-005｜构建彻底失败：`node:path` 被 edge 环境引用

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | `npm run build` 报 `Module not found: Can't resolve 'node:path'`，整个构建过不去 |
| **严重程度** | **高**（完全无法发布） |
| **是否丢数据** | 否 |

### 现象

本地和服务器的构建都失败，报错指向 `node:path` —— 但项目里**没有任何一处直接 import 它**。

### 根因

依赖链一路静态解析过去了：

```
instrumentation.js → lib/scheduler.js → lib/settings.js → lib/db.js → node:path
                                                                       ↑ edge 环境没有这个模块
```

**Next 14 会为 server 和 edge 各编译一次 `instrumentation.js`**。
webpack 顺着这条链静态解析，到了 edge 那一遍就找不到 `node:path` —— 整个 build 挂掉。

### 修复

放弃 `instrumentation.js`，改成**懒启动**：

```js
// 第一个访问 /api/health 或后台审核页的请求会调用它（幂等，重复调用无副作用）
export function startReviewScheduler() {
  if (started) return;
  started = true;
  // ...
}
```

同时删掉 `next.config.mjs` 里的 `experimental.instrumentationHook`。

### 预防措施

- ⚠️ **这个项目不要再用 `instrumentation.js`** —— 这条已经写进 `next.config.mjs`、`lib/scheduler.js`
  和 `docs/CONTENT-REVIEW.md` 三处注释；
- 需要在应用启动时跑的东西，统一走"懒启动"：挂在 `/api/health` 上，第一个请求触发。

## INC-006｜批量任务卡在「进行中」18 小时

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 小米控制台里任务早就完成了，后台却一直显示"进行中" |
| **严重程度** | **中**（钱花了、活也干了，但结果收不回来） |
| **是否丢数据** | 否（结果还在上游，补一次拉取就能救） |

### 现象

批量任务提交成功，后台批次状态永远停在 `submitted`，怎么点「拉取结果」都不动。

### 根因

**查状态和下载结果时误用了「对话接口」的地址**（`config.baseUrl`），而批次是在**批量专用域名**上创建的
（`config.batchBaseUrl`）。两边根本不是一套 API，自然查不到。

### 修复

所有和批量相关的调用统一走 `config.batchBaseUrl`：

```
上传 JSONL     → batchBase /files
创建批次       → batchBase /batches
查状态         → batchBase /batches/{id}
下载结果       → batchBase /files/{id}/content
```

前端「立即提交 / 拉取结果」现在会把每一步的结果逐行显示出来，卡在哪一步一眼能看到。

### 预防措施

**这四个调用一个都不能少、一个都不能用错地址** —— 已经把这条写进 `docs/CONTENT-REVIEW.md`
的排障表和代码注释。

## INC-007｜创建批次一直 500：根因是文档里没写的一个必填字段

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 点「测试批量接口」，返回 `HTTP 500 internal_error`，没有任何有用信息 |
| **严重程度** | **中**（功能整个不可用，但排查花了很久） |
| **是否丢数据** | 否 |

### 现象

创建批次恒定失败，上游只回一句 `internal_error`。试过改 `completion_window`、减任务数、
换模型 —— 都不行。

### 排查过程（这才是值得记的部分）

1. 先做**浅探测**（只上传文件，不建批次）→ 通过，说明地址和 Key 没问题；
2. 再做**深探测**（真建批次）→ 500；
3. 于是写了一个「参数组合矩阵」：`completion_window` × 是否带 `metadata` × 是否带 `name`……
   逐个组合试；
4. **最后在小米控制台的返回体里看到 `"name":"test"`** —— 控制台自己建的任务带了这个字段。
   补上 `name` 之后**一次就过**。

### 根因

**创建批次必须带 `name` 字段，但官方文档里没有写。**

### 修复

```js
name: batchNameOf(kind),   // "Solace·内容审核" / "Solace·日记打标" / "Solace·日记生成"
```

⚠️ 官方文档里写着必填的 `name` 👈 —— **反过来，文档没写的也可能是必填的**。

### 预防措施

- 报错信息里带上**"我们到底发了什么"**：接口路径、`completion_window`、任务数（含图片数）、文件 id。
  上游只回 `internal_error` 时，没有这些参数根本没法定位；
- 后台的「测试批量接口」现在会**逐个组合探测并把 JSONL 原文回显**，下次上游再改协议能立刻看出来。

## INC-008｜PM2 重启了 208 次，日志里却没有任何报错

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | `pm2 list` 里 `↺` 计数已经 208 次 |
| **严重程度** | **中**（表现为"偶尔卡一下"，容易被忽略） |
| **是否丢数据** | 否 |

### 现象

服务隔一阵就重启，但 `pm2 logs` 里看不到任何异常堆栈。

### 根因

**两个内存参数不匹配**：

| 参数 | 值 | 含义 |
|---|---|---|
| Node 的 V8 堆上限 | 约 **1.8G** | 超过它 Node 自己会 OOM |
| PM2 的 `max_memory_restart` | **600M** | 超过它 PM2 主动把进程杀掉重启 |

程序还在 V8 的舒适区（比如 700M）时，PM2 就已经认为"它吃太多了"，直接杀掉重启。
**不是崩溃，是被"预防性"杀掉。**

### 修复

两个值**一起调、并且对齐**：

```js
node_args: "--max-old-space-size=450",   // 让 Node 主动控制在这个水位
max_memory_restart: "700M",              // PM2 的阈值留在它之上
```

### 预防措施

⚠️ **这两个值必须成对设置**。只设 `max_memory_restart` 而不给 Node 一个明确上限，
就是给未来的自己埋雷 —— 而且它不会报错，只会安静地重启。

## INC-009｜「我tm草泥马，你个废物，臭sb」整句一个都没拦住

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 用自己的话测审核词表，一句典型的脏话 0 命中 |
| **严重程度** | **中**（审核形同虚设） |
| **是否丢数据** | 否 |

### 现象

第一次测试词表时，`fuck` 没拦住 —— 因为提示词里只写了"人身攻击"，漏了"脏话本身"。
补完提示词后，用中文样本再测，**整句一个词都没命中**。

### 根因

词表里只有**规范写法**。而真实输入里是：

- 拼音首字母缩写：`sb` / `tm` / `tmd` / `nmsl` / `cnm` / `mdzz`
- 各种变体与谐音
- 中间夹着别的字（`我tm草泥马`）

### 修复

按两个维度重列：

1. **家族** —— 同一个词的所有常见写法归到一起（草泥马 / 草泥馬 / 卧槽 / 我操…）；
2. **拼音缩写单列** —— ⚠️ 这几个**必须用词边界匹配**，否则 `sb` 会命中 `absorb`、`tm` 会命中 `atm`。

### 预防措施

**用真实样本测词表，不要用自己造的例子** —— 造例子时会不自觉地把词写成规范形式，
而那恰好是词表覆盖得最好的情况。

## INC-010｜审核 AI 读不懂格式时，曾经的默认行为是"按通过处理"

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 用户在验收时指出："读不懂就当通过，这不是等于不审吗" |
| **严重程度** | **中高**（可能放过违规内容 —— 属于设计缺陷，不是实现 bug） |
| **是否丢数据** | 否 |

### 现象

AI 返回的内容不符合约定格式时，代码打一行日志"AI 返回的不是约定格式，按通过处理"，然后放行。

### 根因

**默认值的方向错了。** 审核这种系统，遇到"判断不了"的情况，
默认必须是**更保守的那一侧**（交人工），而不是更省事的那一侧（放行）。

### 修复

判定的返回值从两态改成**三态**：

```
明确 pass   → 清掉「未审核」标记
明确 reject → 回填默认值
读不懂      → 标 failed，进人工队列
```

### 预防措施

⚠️ **审核类系统的默认分支必须是"不确定"**。写这类代码时问自己一句：

> 如果这一段永远走不到正常路径、只能走默认分支，最坏结果是什么？

如果答案是"违规内容被放行"，那这个默认值就是错的。

## INC-011｜`[RISK:no]` 标记漏进用户气泡

**现象**：安全模式下 AI 回复里的 `[RISK:no]`（内部标记）被用户直接看到。

**根因**：这个标记是"给系统的信号"，但**流式是一个字一个字发出去的** —— 后端要等流结束才读得到它，那时它早在用户屏幕上了，**收不回来**。

更麻烦的是**三条通路**都会把文本送出去：流式回调、定稿（`finishReveal`）、落库。第一次只堵了流式回调，标记从"定稿"那条又漏了出来。

**修复**（三层，缺一不可）：

1. **前端渲染前统一剥掉**：`replace(/\[RISK[^\]]*\]/gi, "")` —— 不看标记在哪、有几处，一律剥。
2. **后端扣住开头 40 字**：模型有时把标记写在前头，那 40 字攒够再发。
3. **`askAI` 的两个 `return` 也过滤** —— 定稿和落库用的正是这个返回值。

**预防**：

- 正则写 `\[RISK[^\]]*\]` 而不是 `\[RISK:\w+\]` —— 模型可能写成 `[RISK: no]`（带空格）或 `[RISK_NO]`。
- **任何"给系统的标记"都要假定两件事**：模型不会照格式写；它会写在你想不到的位置。
- 同类问题（自定义协议标记）以后一律走"**渲染前剥掉**"，不要在流式传输里想办法。

## INC-012｜全站白屏：构建完没重启 pm2

**现象**：首页、后台、手机端**全部**白屏；无痕模式也一样；"只有文字、没有样式"。

**根因**：`npm run build` 跑了，但 **`pm2 delete` + `pm2 start` 没跑**。

旧进程还在内存里持有旧代码 → 它渲染的 HTML 引用**旧的 CSS 文件名** → 而 `rm -rf .next` 已经把旧 CSS 删了 → 静态资源 **400** → 全站没样式、JS 也没接管。

**怎么一眼认出来**：对比"HTML 里引用的文件名"和"磁盘上实际的文件名" —— HTML 要 `56ef297407a3b3fe.css`、磁盘上是 `2b3bbedb54a38807.css`，**对不上就实锤**。

⚠️ 注意那时 **JS chunk 全是 200**（内容没变、文件名就没变），只有 CSS 变了 —— 所以"部分 200 部分 400"也是这个原因，不是 Nginx 的锅。

**修复**：`pm2 delete solace && pm2 start ecosystem.config.js`（几秒）。**但更根本的是顺序问题，见 INC-014。**

**预防**：

- **构建和重启必须连着做**。中间断了就是"新产物在磁盘、旧代码在内存"这种半吊子状态。
- 症状特别容易误判：无痕也白 → 以为代码有 bug；直连 3000 也 400 → 以为 Nginx 配置问题。

## INC-013｜502：用 shell 替换代码时，反引号被吃掉了

**现象**：`npm run build` 报 `Expression expected`，指向一行**看着完全正常**的代码。

**根因**：用 PowerShell 的 `.Replace()` 批量改代码，而 **PowerShell 把反引号当转义符**。生成的代码里两个反引号凭空消失：

- 原本：`const replyToSave = interrupted ? \`${safeReply}（回复中断）\` : safeReply;`
- 变成：`const replyToSave = interrupted ? ${safeReply}（回复中断） : safeReply;`

→ 语法错误 → 构建失败 → 站点 502。

**修复**：用 `[char]96` 把反引号拼出来（PowerShell 认不出这个字符就不会吃），或改用不做转义处理的编辑方式。

**预防**：

- **改带模板字符串 / 反引号 / `${}` 的代码，别用 shell。**
- shell 批量替换只适合**纯 ASCII、无特殊字符**的字面量。
- ⚠️ 这个坑**之前就踩过**（项目笔记里记着），这次又踩 —— 所以写进这里，**不靠记忆**。

## INC-014｜部署链用 `&&` 串起来 + `pm2 stop` 在最前 → SSH 一断整站 down

**现象**：SSH 断开后站点彻底打不开（`pm2 list` 显示 `stopped`，`curl` 返回 `000`）。

**根因**：部署是一条 `&&` 链：`pm2 stop solace && rm -rf .next && npm run build && pm2 delete && pm2 start`。

**SSH 一断，链子就停在中间** —— 而 `pm2 stop` 排在**最前面**，所以最坏情况是"进程停了、`.next` 还被删了、构建没跑完"。实际就发生成这样：日志停在断线那一刻，站点直接 down。

**修复**：

1. **调换顺序** —— 先 `npm run build`（这期间站点仍跑旧版），**构建成功之后**再 `pm2 delete && pm2 start`（只要几秒）。SSH 再断，最坏也只是"构建失败，旧版还在跑"。
2. **长任务加断线防护** —— `nohup npm run build > /tmp/build.log 2>&1 &`，断了也能接着跑。
3. **`rm -rf .next` 可以省掉** —— `next build` 会自己覆盖。省掉它，构建期间连"产物被删"的风险都没有了。

**预防**：

- **任何"会停服务"的步骤都要排在最后**。构建、拷贝、解包这些都不影响线上。
- 部署脚本里**别用 `&&` 把"停服务"和"构建"串成一条命令**。
- 已加 `scripts/check-deploy.sh`（部署完跑一遍出 ✅/❌ 清单）和 `scripts/test-keywords.mjs`（词表回归测试，退出码可当门禁）。

## INC-015｜手机端音乐永远不响：自动播放解锁选错了事件

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-25（发现）|
| **发现方式** | 用户反馈"手机端听不了歌"，桌面端一直正常 |
| **严重程度** | **中** —— 功能在手机上完全不可用，但不丢数据、不影响其他功能 |

### 现象

1. 桌面进站后触摸/点击任意位置，音乐自动响起，一切正常；
2. 手机上无论怎么点，音乐就是不自动响；
3. 更糟的是**没有任何报错提示** —— 错误文案写在展开面板里，面板收起时用户根本看不到。

### 根因

自动播放解锁监听的是 `pointerdown` / `touchstart` —— 但按 HTML 规范（activation triggering
input event），**这两个事件不构成"用户激活"**。手机浏览器（尤其 iOS Safari）要求 `play()`
必须在手势**完成**的事件里调用：首次触摸时在 pointerdown 里调 `play()`，直接被
`NotAllowedError` 拒绝。

雪上加霜的是失败路径：旧实现里解锁标记 `unlockedRef` 在 play 之前就置位了，`once` 监听
触发一次即移除 —— **失败后永远不会重试**，音乐从此哑掉。

为什么桌面一直没事？**Chrome 对 pointerdown 处理器里的 `play()` 比较宽容**（手势处理中），
把 bug 完全掩盖了。这也解释了"桌面能听、手机不能"的不对称现象。

### 修复（components/MusicPlayer.jsx）

1. **解锁事件换成真正的激活事件**：`pointerup` / `touchend` / `click` / `keydown`。
   同一次触摸会连发 pointerup → touchend → click，等于给三次机会，浏览器认哪个用哪个；
2. **失败可重试**：去掉 `{ once: true }`，play 失败时重置解锁标记，下一次任意交互自动再试
   （用户点开面板的那一下就会自动接上音乐）；
3. **错误可见**：面板收起时小球右上角显示红点，点开就能看到失败原因。

### 预防

- **凡是涉及"浏览器手势 / 自动播放"的代码，先查规范里的激活事件列表再选事件**，
  不要凭直觉认为"按下就算手势"——触摸的激活事件是"抬起"不是"按下"；
- **失败路径必须有用户可见的反馈**，不能只写在默认收起的容器里（这次 errorMsg 只在展开
  面板里，用户端表现为"毫无动静"，排查时无法从现象收敛）；
- 涉及浏览器策略的功能（自动播放、通知、摄像头等）**必须真机双端验证**，
  桌面 Chrome 的宽容行为会掩盖移动端的严格限制。

## INC-016｜"部署成功了"但用户端还是旧代码：构建败在 lint，而 `✓ Compiled successfully` 早已打印

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-10-03 |
| **发现方式** | 用户反馈"AI 消息里还带着 `[温柔]` 标签"（该标签只该用于朗读、展示时要剥掉），同期出现过一次 502 |
| **严重程度** | **高** —— 线上长期处于"服务端像新的、客户端像旧的"的不一致状态，且每次部署都在重演 |
| **是否丢数据** | **否** —— 数据与配置都正常 |

### 现象

1. 按流程 `\cp -rf` 覆盖代码 → 构建（屏幕上明明打印了 `✓ Compiled successfully`）→ 重启；
2. 新接口能用（`GET /api/tts/config` 返回新字段），但**用户端行为没变**：气泡里的朗读标签照旧显示；
3. 期间还出现过一次 502，重启后自行恢复。

### 根因

两条叠在一起：

1. **`npm run build` 一直在失败，只是失败点在最末尾的 lint**：
   `components/StickerPanel.jsx` 两处 JSX 文本里有裸的 `"`，触发
   ESLint `react/no-unescaped-entities`（Error 级别）→ 构建以**退出码 1** 结束；
2. **判据错了**：Next 的顺序是「编译 → lint → 收尾」，所以
   `✓ Compiled successfully` 在 **lint 之前**就打印了。而本项目的"构建成功判据"
   （`AGENTS.md`、`DEPLOY.md`、`README.md`、`docs/OPERATIONS.md`、`docs/DEPLOY-CHECKLIST.md`、
   `docs/INCIDENTS.md` 六处，以及所有人养成的习惯）恰好就是"看到那一行"——
   于是**看到的和实际发生的相反**。

失败发生在收尾阶段，`.next` 就成了**半成品**：编译期写入的路由文件、chunk 都是新的，
但清单 / `BUILD_ID` 没更新完。于是：
- 服务端能路由到新接口（所以"看起来更新了"）；
- HTML 仍按旧清单引用旧的客户端 chunk → **浏览器执行的还是旧 JS**（所以展示侧不剥标签）。

### 修复

1. `components/StickerPanel.jsx` 那两行的 `"` → `&quot;`（渲染结果完全一致）。
   现在 `npm run lint` 0 Error、`npm run build` **退出码 0** 且末尾正常打印 Route 表；
2. 判据改成**退出码 0 + 末尾 Route 表**，部署命令写成
   `npm run build || { echo "❌ 构建失败（退出码 $?）—— 别重启"; exit 1; }`；
3. 六处文档同步改判据，`AGENTS.md`「这个项目特有的坑」新增一行
   **`✓ Compiled successfully` ≠ 构建成功**。

### 预防

- **凡是"看日志里某一行"的成功判据，都要先确认那一行相对于失败点是在前还是在后。**
  更稳的判据永远是**退出码**：`npm run build || exit 1`；
- 部署流程里**"构建"与"重启"之间必须有护栏** —— 构建失败要挡住重启，
  否则等于把半成品的 `.next` 推给用户（这类故障的隐蔽性远高于"直接构建失败"）；
- **"接口是新的、界面是旧的"这种半新半旧现象，第一反应就该怀疑构建产物不完整**，
  而不是去翻前端业务代码 —— 这次差点把本来正确的剥离逻辑重写一遍。

## INC-017｜切换账号（退出 A 登录 B）首屏聊天会话与气泡串台泄露

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-11-05 |
| **发现方式** | 用户在同一浏览器测试退出账号 A、登录账号 B，刚进入 `/chat` 时第一眼显示的是账号 A 的全部会话列表与聊天气泡 |
| **严重程度** | **极高** —— 属于严重的跨租户/跨账号隐私数据串台与泄露风险 |
| **是否丢数据** | **否** —— 服务端数据正常，是客户端缓存与首屏无主盲读造成的数据错乱渲染 |

### 现象

1. 用户在聊天页正常退出登录账号 A，页面跳至登录页；
2. 登录另一个全新的账号 B，进入 `/chat`；
3. 界面并未展示空的新建对话页，而是瞬间将账号 A 退出前的会话列表和全部聊天记录完整展现在屏幕上，数秒后网络响应回来才发生跳变。

### 根因

1. **缓存无主单例键与跨账号模糊扫描**：`lib/message-cache.js` 维护了全局单例的 `solace_last_active_conv` 与 `solace_convs_latest` 兜底，且在 `findCachedMessages` 中有无条件遍历 localStorage 匹配 convId 尾部的逻辑；
2. **退出登录未清空私有存储**：前端退出登录时仅清除了会话 Cookie 和欢迎标记，本地保留了全部会话列表、消息缓存与草稿；
3. **首屏生命周期盲目回填**：`app/chat/page.js` 首屏组件挂载时，在当前登录用户身份（`user.id`）尚未获取到的时间窗口内，立即从本地单例键恢复了上次会话 ID，并由模糊扫描直接命中了账号 A 的消息缓存。

### 修复

1. **废除全局兜底，强制 userId 隔离**：重构 `lib/message-cache.js`，彻底移除 `latest` 兜底和模糊扫描，所有本地会话与消息读写强制要求有效 `userId`；
2. **登出彻底清理机制**：新增 `clearAllLocalChatState()`，登出时彻底清空 localStorage 中所有消息缓存、会话列表、活跃会话标记及内存 state；
3. **严格用户身份校验后挂载**：`app/chat/page.js` 移除无主初始化，必须在确认当前登录身份后才恢复其专属数据；新账号纯净展示新建对话页。

### 预防

- **任何客户端存储（localStorage / sessionStorage / 内存缓存），只要存储的是用户私有业务数据，KEY 必须强制绑定当前 `userId`**，严禁使用全局无主单例键；
- **登出流程必须全量清空私有存储**，不给任何跨账号数据留存机会；
- **未确认用户身份前，绝对禁止盲目将本地缓存数据渲染为业务界面**。

- **暗黑模式设计中，背景色与文本色必须同级适配，严禁只对文字做全局 `!important` 浅白反转而放任背景色保持局部浅色**；

## INC-019｜测评"看着存了、刷新就没了"：`type` 列宽不足导致长 ID 插入静默失败

| **是否丢数据** | **是** —— 提交的测评数据由于 SQL 异常未写入数据库，已答内容丢失 |

### 现象

1. 用户在治愈小屋或量表测评页完整回答了一套心理量表（如自我关怀量表），点击提交后界面正常展示了评估分数与建议卡片；
2. 刷新页面或再次点击「历史记录」弹窗，列表为空；
3. 后台数据库 `assessment_results` 表中没有任何该条测评的写入痕迹。

### 根因

1. **表结构列宽过窄**：`assessment_results.type` 建表时定义为 `VARCHAR(16)`；
2. **业务允许的量表 ID 长度远超列宽**：自定义量表的标识符规则允许 2~63 字符（例如 `self-compassion-scale` 长达 21 字符）；
3. **严格模式抛错被前端静默吞掉**：生产环境 MySQL 开启了严格模式（STRICT_TRANS_TABLES），INSERT 触发 `Data too long for column 'type'` 直接中断；而前端提交逻辑使用了静默 catch，并在组件内执行了本地伪乐观展示，导致"界面看起来成功、底层全失败"。

### 修复

1. **扩列与幂等迁移**：建表语句升级为 `VARCHAR(64)`；在 `lib/schema.js` 的 `ensureUserColumnsOnce()` 中加入幂等迁移检测，查询 `information_schema` 当列宽小于 64 时自动执行 `ALTER TABLE ... MODIFY type VARCHAR(64)`；
2. **入参校验对齐**：`app/api/user/assessments/route.js` 的类型上限校验由 16 放宽到 64；
3. **废除伪乐观，异常显式暴露**：移除前端虚假成功的本地 optimistic 写入，卡片展示与历史刷新严格以接口实际返回为准；提交失败时显式提示"测评结果已生成但未能存入云端"。

### 预防

- **建表设计时，标识符 / 枚举 / 类型字段严禁卡死在"刚好够用"的极端值**，至少预留 64~128 字符冗余应对业务扩展；
- **前端严禁对后端关键持久化接口进行盲目捕获吞错（Silent Catch）并伪造成功状态**，接口失败必须向用户明确反馈。

## INC-020｜生日主动祝福触发变量暂时性死区（TDZ）导致页面运行时崩溃白屏

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-10-28 |
| **发现方式** | 用户访问 `/chat` 页面发生运行时崩溃白屏，控制台报错 `ReferenceError: Cannot access 'displayName' before initialization`；但 `next build` 构建全程绿灯通过 |
| **严重程度** | **高** —— 核心聊天界面 100% 崩溃白屏不可用 |
| **是否丢数据** | **否** —— 纯前端运行时语法与生命周期崩溃 |

### 现象

1. 本地及服务器执行 `npm run build` 成功完成，没有任何静态语法报错，ESLint 检查 0 error；
2. 在浏览器中打开 `/chat` 聊天主界面，页面瞬间白屏崩溃；
3. 开发者工具控制台抛出：`Unhandled Runtime Error: ReferenceError: Cannot access 'displayName' before initialization`。

### 根因

1. **ES6 变量暂时性死区（TDZ）**：在 `app/chat/page.js` 中新增了生日识别与主动祝福逻辑，其中一个 `useEffect` 副作用钩子的依赖数组直接引用了 `displayName`；
2. **声明位置倒置**：`displayName` 变量定义在组件代码的后半段（约 500 行之后），而组件挂载阶段运行的前置 Effect 先于该行执行，在词法作用域内访问了尚未初始化的 `const` 变量；
3. **构建期检测盲区**：`next build` 进行静态预渲染（SSG/SSR）阶段时，并不执行客户端特定的交互副作用（如 `useEffect` 内部生命周期），静态分析无法检测出运行时 TDZ 引用倒置。

### 修复

1. **解耦作用域依赖**：移除 Effect 对后置变量 `displayName` 的引用，改为在 Effect 内部自行计算昵称（`profile.username → 邮箱前缀 → "你"`）；
2. **依赖项收敛**：Hook 依赖数组收紧为确定的响应式状态（`profile.username`），避免跨作用域捕获临时派生变量。

### 预防

- **`next build` 构建成功不等于前端无运行时死区（TDZ）**，凡涉及生命周期 Hook（`useEffect`、`useCallback`）的代码改动，**必须在真实浏览器环境中实际访问页面进行全链路测试**；
- **严格遵循变量“先声明、后使用”的原则**，全局或跨段落复用的派生变量应置于组件顶部，或直接封装为纯函数/独立 Hook。

## INC-021｜压力放松提醒静默失效：状态无过期窗与仪表盘收起导致四重链条阻塞

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-23 |
| **发现方式** | 用户在聊天中多次表达焦虑且压力分值持续超标，但系统从未弹出过放松提醒与干预卡片 |
| **严重程度** | **中高** —— 心理健康干预核心功能静默瘫痪，未能及时为高压用户提供疏导 |
| **是否丢数据** | **否** |

### 现象

1. 用户与 AI 连续对话，多次表达极度焦虑与压力，后台压力打分明显处于高位（>70 分）；
2. 系统从未弹出过建议呼吸放松或蝴蝶拍的干预提示卡片；
3. 管理员在后台修改压力提醒阈值后，前台依然无任何提醒反应。

### 根因

排查发现该功能链路上存在 **4 个独立的致命阻塞点**，任何一个都足以造成静默失效：
1. **进行中状态无超时窗口**：用户只要曾经点过一次「现在做」放松练习，若中途切走或关闭页面未点击「做完了」，该「正在放松中」标记将**永久锁定**，阻断后续所有干预；
2. **阈值覆盖优先级错误**：前台读取逻辑为 `state.threshold || 后台配置`，而用户表中该字段默认值为 `70`，导致后台无论怎么调低阈值均被用户表的默认非空值完全覆盖；
3. **收起仪表盘中断轮询**：仪表盘组件内部写有 `if (hidden) return;`，用户一旦点击右上角「×」收起仪表盘，**前端轮询检测定时器立即停止**，聊天场景完全依赖此轮询，导致收起后提醒功能彻底下线；
4. **时序倒置需多一次触发**：“连续两次高压”的判定逻辑查的是数据库最近 2 条记录，但业务代码**先做判定后执行写库**，当前高压记录尚未落库，实际需要连续 3 次才能触发。

### 修复

1. **设置 2 小时自愈滑动窗口**：放松状态增加时间窗口，超过 2 小时未完成自动失效重置，解开死锁；
2. **支持阈值级联跟随**：阈值逻辑重构为 `0 = 跟随后台全局配置`，通过 `resolveThreshold` 统一收敛解析；
3. **轮询与 UI 渲染解耦**：组件视觉收起后保持后台静默轮询，保障弹窗干预随时可触发；
4. **时序校正**：判定逻辑调整为“当前评分记录 + 数据库最近一条记录”，精准命中“连续两次”阈值。

### 预防

- **状态机设计必须具备超时与自愈机制（TTL）**，不能假设用户一定会走完闭环（如点击“完成”），未完成的瞬态不能成为永久阻塞；
- **后台全局配置与个体用户配置必须设计明确的“继承”逻辑**（如 0 或 null 代表继承），避免老库默认值封死后台管控；
- **核心后台检测与业务轮询不得与纯展示型 UI 的折叠/展开生命周期强行绑定**。

## INC-022｜日记标签外露 `reject`：后台人工审核分流缺失导致脏数据污染业务库

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-23 |
| **发现方式** | 用户在个人日记页面浏览时，发现日记卡片上突兀地展示了一个名为 `reject` 的荒谬情绪标签 |
| **严重程度** | **中** —— 内部管理后台运维状态字泄露到用户业务界面，破坏陪伴与治愈氛围 |
| **是否丢数据** | **否** —— 但污染了 `diaries.mood` 字段数据 |

### 现象

1. 用户日记卡片本应显示「平静」、「开心」或「疲惫」等温和的情绪标签；
2. 某篇日记的标签位置直接渲染了英文单词 `reject`。

### 根因

1. **管理后台动作未分流**：管理员在后台「数据审核」列表对一项**日记打标**任务点击了「驳回」；
2. **接口缺乏语义隔离**：审核判决接口 `applyManualVerdict` 未区分任务类型，直接将审核判决值 `verdict: "reject"` 传给了底层写入逻辑；
3. **底层直接落库**：`applyVerdict` 误将 `reject` 作为情绪词直接执行了 `UPDATE diaries SET mood = 'reject'`；
4. **前端裸渲染无白名单**：前端卡片组件通过 `{d.mood}` 直接输出了库中内容，缺乏容错拦截。

### 修复

1. **底座增加白名单校验**：`applyVerdict` 增加强校验，只允许 8 个标准情绪词落库，非法值一律退回默认标签；
2. **管理动作语义修正**：对日记打标任务点击「驳回」定义为“撤销标签/清空标签”，严禁将动作英文代号当内容写入；
3. **后台列表物理分流**：管理后台「数据审核」与「日记打标」拆分独立视图与接口，杜绝跨业务误操作；
4. **前端组件白名单防御**：封装 `MoodBadge` 组件，非白名单内的脏值直接隐藏不予渲染；
5. **历史数据幂等清洗**：上线时通过脚本自动清洗已写入历史脏数据的 `reject` 记录。

### 预防

- **严禁将系统管理动作（如 pass, reject, pending）直接作为业务数据落库**；
- **前后端展示层必须建立强白名单约束（Defense in Depth）**，绝不直接将数据库未清洗字段裸露在终端 UI。

## INC-023｜阿里云百炼 CosyVoice 语音流式合成报 `[cosyv…` 彻底阻断朗读

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-11-05 |
| **发现方式** | 管理员在后台测试语音合成正常，但在前台聊天界面点击播放 AI 朗读时 100% 报错并弹出 `DashScope 语音流式生成报错：[cosyv…`，无法朗读 |
| **严重程度** | **高** —— 语音朗读功能完全不可用，影响所有接入百炼语音合成的用户 |
| **是否丢数据** | **否** |

### 现象

1. 后台配置阿里云百炼 CosyVoice 语音服务，点击测试试听功能正常；
2. 用户在 `/chat` 界面进行对话，AI 回复后点击小喇叭朗读按钮；
3. 界面弹出红色提示 `DashScope 语音流式生成报错：[cosyv…`，音频流立即中断，无声。

### 根因

1. **跨供应商专有标签混淆**：系统为小米 MiMo 研发了专有的语气与动作标签注入机制（如 `[温柔]`、`[叹气]`），但在切换至百炼 CosyVoice 时，由于未物理隔离不同厂商的文本预处理管道，这些方括号专有标签被原样发给了百炼 API；CosyVoice 文本前端解析器（Text Frontend）将其当成非法协议格式，直接抛出 HTTP 411 客户端错误；
2. **调用参数不兼容**：请求百炼时错误传入了 CosyVoice 不支持的 `instruction` 参数；
3. **错误截断掩盖真相**：前端通用提示组件（`showHint`）设置了最大 25 个字符的强制截断，将长异常堆栈直接切断在 `[cosyv...` 处，导致关键的错误码和异常原因被切掉，排查人员无法直接看出是 411 还是网络问题。

### 修复

1. **供应商文本管道物理隔离**：在调用百炼 DashScope 之前，对待朗读文本执行深度清洗，彻底剔除所有内部方括号标签及语气修饰；
2. **参数解耦**：移除百炼请求体中不支持的扩展参数，保持与官方 SDK 规范严格对齐；
3. **取消破坏性错误截断**：调整前端错误提示策略，保留关键错误码与描述，便于第一现场定位排障。

### 预防

- **多模型/多服务商架构下，特定厂商的专有协议（如 MiMo 的语气标签、特殊控制符）必须在适配层末端彻底清洗或严格隔离**，严禁未经适配将 A 厂私有语法传给 B 厂；
- **开发与排障期间的前端异常捕获，严禁对服务端返回的 Error Message 进行破坏性短截断**。
