## INC-001｜日记页数据"消失"：引用了不存在的导出函数

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-20 |
| **发现方式** | 用户在日记页刷新后发现列表为空；但后台能看到全部日记 |
| **严重程度** | **高** |
| **是否丢数据** | **否** —— 数据一直完好，只是接口 500 导致前端渲染不出来 |

### 现象

1. 首页、聊天页均正常，**只有日记页刷新后列表为空**；
2. 情绪标签从来不出现；
3. 后台「用户数据 → 日记」能看到全部日记 —— 说明数据在库里好好的。

### 根因

`app/api/user/diaries/route.js` 与 `app/api/user/diaries/mood/route.js` 里写的是：

```js
import { ensureDiaryColumnsOnce } from "@/lib/schema";
```

但 `lib/schema.js` **从未导出过 `ensureDiaryColumnsOnce`**。它实际导出的是：

- `ensureDiaryColumns()` —— 没有 `Once` 后缀
- `ensureUserColumnsOnce()` —— 内部已经包含 diaries 的补列

于是运行到这一行时抛 `TypeError: ensureDiaryColumnsOnce is not a function`，
接口直接返回 500，前端拿不到日记列表。

### 为什么构建没拦住

`next build` 遇到"导入了不存在的命名导出"时通常**只给警告**，把它当成 `undefined` 放过去，
**构建照常成功**。只有真正请求那个接口才会崩 —— 典型的 **"构建通过 ≠ 功能正常"**。

### 修复

两处 import 与调用统一改为 `ensureUserColumnsOnce()`。同时做了两项加固：

1. **补列失败不再拖垮主流程** —— `ensureUserColumnsOnce()` 在 diaries / conversations / messages
   等接口里都用 `try/catch` 包住：即使补列失败（例如数据库账号没有 `ALTER` 权限），
   用户依然能看到自己的数据；
2. 前端 `requestDiaryMood` 的失败分支加了一行 `console.warn`（对用户仍然静默），
   便于现场排查。

### 预防措施（已纳入流程）

1. **新增跨模块引用后，必须实际请求一次那个接口** —— 不能只以"build 成功"为准；
2. "某个功能突然不可用、但其他都正常"时，**第一件事看服务端日志**：
   `TypeError` / `is not a function` 会直接打在那里；
3. 涉及"升级兼容"的自动补列 / 自动修复逻辑，**一律用 `try/catch` 包住**，
   不允许影响主流程；
4. 协作场景下，**同一份代码分发给别人之前，先自测关键路径**（日记列表与新增、发消息、登录），
   避免把缺陷扩散出去。

### 相关文件

- `app/api/user/diaries/route.js`
- `app/api/user/diaries/mood/route.js`
- `lib/schema.js`
- `app/chat/page.js`

## INC-002｜域名 502 / 应用 500：同一项目跑了两个实例

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-19 ~ 09-20 |
| **严重程度** | **高**（反复出现多次） |
| **是否丢数据** | 否 |

### 现象

- 用域名访问报 `502 Bad Gateway`（Nginx），或页面只有一句 `Internal Server Error`；
- 但 `http://127.0.0.1:3000` 或 IP 直连却是正常的；
- 改了代码后页面没变化，"一半生效一半不生效"。

### 根因

服务器上**同时跑了两个实例**：

| 端口 | 谁启动的 |
|---|---|
| 3000 | pm2（`ecosystem.config.js`） |
| 3001 | 宝塔「Node 项目」 |

Nginx 的 `proxy_pass` 指向了其中一个，而那个恰好是**在构建产物残缺时启动、之后没重启过**的旧进程。

叠加的另一个因素：`rm -rf .next` 之后 `npm run build` 没有成功（内存不足被系统杀掉），
`.next` 处于残缺状态，进程启动时直接报：

```
Could not find a production build in the '.next' directory.
```

### 修复

1. 只保留一个实例：停掉宝塔的 Node 项目（**只停别删**，删除可能连站点配置一起删掉），
   或反过来 `pm2 delete solace`；
2. Nginx 的 `proxy_pass` 指向正在跑的那个端口；
3. `rm -rf .next` → `npm run build`（确认 `✓ Compiled successfully`）→ `pm2 start`；
4. 加 2G swap，避免构建时内存不足被 OOM 杀掉。

### 预防措施

- **只保留一个实例**，随时用 `ss -lntp | grep -E ':3000|:3001'` 确认；
- **构建前后**：`pm2 stop solace` → `npm run build` → `pm2 start solace`；
- **构建产物更新后，所有跑着旧产物的进程都必须重启**。

## INC-003｜MySQL 被系统杀掉，导致全站卡住后 500

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-20 |
| **严重程度** | **高** |
| **是否丢数据** | 否 |

### 现象

- 所有请求先**卡住很久**（十几秒），然后返回 500；
- `curl http://127.0.0.1:3000/api/health` 也是长时间无响应后 500；
- 与"代码写错"的区别很明显：**代码错误是秒返回**。

### 根因

`systemctl status mysqld` 显示 `inactive (dead)` —— MySQL 被停了。
时间点与 `npm run build` 高度吻合：**构建占满内存，内存不足时系统杀掉了 MySQL 进程**。

应用侧表现出的"卡住"，是在等数据库连接超时（`connectTimeout: 8000`）。

### 修复

```bash
systemctl start mysqld
systemctl enable mysqld      # 顺带打开开机自启
pm2 restart solace           # 让应用重建数据库连接
curl -s https://你的域名/api/health
```

### 预防措施

1. 内存小的服务器**先加 2G swap**；
2. **构建前先 `pm2 stop solace`**，把内存让给构建；
3. 打开 MySQL 的开机自启；
4. 接一个外部监控探针指向 `/api/health`，挂了能第一时间收到提醒。

## INC-004｜AI 回应错位：日记写"开心"，它却回"我读到你很累"

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09-20 |
| **发现方式** | 用户在日记里写"我好开心"，让 AI 读，AI 回"读到了你很累" |
| **严重程度** | **中**（不影响数据，但严重损伤体验 —— 用户会觉得"AI 根本没在听我说话"） |
| **是否丢数据** | 否 |

### 现象

日记正文与 AI 的回应**牛头不对马嘴**：内容明显是正向的，AI 却按"用户情绪低落"来安慰。

### 根因

**给 AI 的指令里写了具体的情绪示例**，模型会直接照抄那个示例的情绪，而不是去读用户真正写了什么。

前端「读日记」的指令原文（`app/chat/page.js` 的 `DIARY_INSTRUCTION`）：

```
你刚刚读了用户的日记，请以陪伴者身份自然地回应。
可以自然引用日记里的具体细节或情绪（比如"你提到今天很累""你写的那段话我记下了"），
然后给予一定安慰，并向用户表示如果可以继续倾诉。
```

两个问题叠在一起：

1. **示例本身是一个负面情绪** —— "你提到今天很累"被当成模板套用；
2. **"然后给予一定安慰"** —— 这句话预设了"用户状态不好"，等于要求 AI 先假设用户难过。

同样的示例也出现在另两处：

- `app/chat/page.js` 的 `SYSTEM_PROMPT`（前端兜底人设）；
- `lib/settings.js` 的 `ai.systemPrompt`（后台默认提示词）。

### 为什么不是后端的问题

链路是通的，逐段验证过：

| 环节 | 实际内容 |
|---|---|
| 前端调用 | `diaryContext: diary.content` —— 传的确实是当前这篇日记的正文 |
| 前端消息构造 | 用户消息里只放标题，正文单独走 `diaryContext` 字段（设计正确） |
| 后端 `/api/chat` | 按 `diaryPrompt` 模板把正文注入成 system 消息（正确） |

所以数据一路是对的，**是最后一步"怎么跟模型说话"出了问题**。

### 修复

三处统一改成：**不给情绪示例，改为要求模型先判断真实情绪**。

```
1. 用户倾诉时，你的第一句话必须先回应他的感受，让他觉得被听见。
   不要预设他的情绪是负面的 —— 他分享开心的事就一起高兴，难过的时候才轻轻接住。
```

读日记的指令也改成：

```
先读懂日记里真实的情绪：是开心的就一起高兴，是低落的才给予安慰，不要预设用户状态不好。
```

> ⚠️ **注意**：提示词存在数据库里，改 `lib/settings.js` 的默认值**不会影响已经存在的配置**。
> 所以线上还需要在后台「对话 AI」页面手动改一遍第 1 条。

### 教训（写 AI 指令时的通用原则）

1. **不要给具体情绪的示例** —— 模型对示例的模仿远强于对规则的遵守。想要它"随机应变"，
   就要写"先判断真实情绪"，而不是举例让它套；
2. **警惕预设性措辞** —— "给予安慰""安抚他"这类词本身就暗示了用户的情绪方向；
3. **改提示词后要回归测试** —— 至少用"正向内容"和"负向内容"各测一次，确认两种都能正确回应；
4. 提示词存在数据库时，**代码里的默认值只是给新装用的**，线上一律以后台配置为准。

### 相关文件

- `app/chat/page.js`（`DIARY_INSTRUCTION` / `SYSTEM_PROMPT`）
- `lib/settings.js`（`ai.systemPrompt` 默认值）
- 后台「对话 AI」页面的线上配置（需手动同步）

## INC-005｜构建彻底失败：`node:path` 被 edge 环境引用

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | `npm run build` 报 `Module not found: Can't resolve 'node:path'`，整个构建过不去 |
| **严重程度** | **高**（完全无法发布） |
| **是否丢数据** | 否 |

### 现象

本地和服务器的构建都失败，报错指向 `node:path` —— 但项目里**没有任何一处直接 import 它**。

### 根因

依赖链一路静态解析过去了：

```
instrumentation.js → lib/scheduler.js → lib/settings.js → lib/db.js → node:path
                                                                       ↑ edge 环境没有这个模块
```

**Next 14 会为 server 和 edge 各编译一次 `instrumentation.js`**。
webpack 顺着这条链静态解析，到了 edge 那一遍就找不到 `node:path` —— 整个 build 挂掉。

### 修复

放弃 `instrumentation.js`，改成**懒启动**：

```js
// 第一个访问 /api/health 或后台审核页的请求会调用它（幂等，重复调用无副作用）
export function startReviewScheduler() {
  if (started) return;
  started = true;
  // ...
}
```

同时删掉 `next.config.mjs` 里的 `experimental.instrumentationHook`。

### 预防措施

- ⚠️ **这个项目不要再用 `instrumentation.js`** —— 这条已经写进 `next.config.mjs`、`lib/scheduler.js`
  和 `docs/CONTENT-REVIEW.md` 三处注释；
- 需要在应用启动时跑的东西，统一走"懒启动"：挂在 `/api/health` 上，第一个请求触发。

## INC-006｜批量任务卡在「进行中」18 小时

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 小米控制台里任务早就完成了，后台却一直显示"进行中" |
| **严重程度** | **中**（钱花了、活也干了，但结果收不回来） |
| **是否丢数据** | 否（结果还在上游，补一次拉取就能救） |

### 现象

批量任务提交成功，后台批次状态永远停在 `submitted`，怎么点「拉取结果」都不动。

### 根因

**查状态和下载结果时误用了「对话接口」的地址**（`config.baseUrl`），而批次是在**批量专用域名**上创建的
（`config.batchBaseUrl`）。两边根本不是一套 API，自然查不到。

### 修复

所有和批量相关的调用统一走 `config.batchBaseUrl`：

```
上传 JSONL     → batchBase /files
创建批次       → batchBase /batches
查状态         → batchBase /batches/{id}
下载结果       → batchBase /files/{id}/content
```

前端「立即提交 / 拉取结果」现在会把每一步的结果逐行显示出来，卡在哪一步一眼能看到。

### 预防措施

**这四个调用一个都不能少、一个都不能用错地址** —— 已经把这条写进 `docs/CONTENT-REVIEW.md`
的排障表和代码注释。

## INC-007｜创建批次一直 500：根因是文档里没写的一个必填字段

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 点「测试批量接口」，返回 `HTTP 500 internal_error`，没有任何有用信息 |
| **严重程度** | **中**（功能整个不可用，但排查花了很久） |
| **是否丢数据** | 否 |

### 现象

创建批次恒定失败，上游只回一句 `internal_error`。试过改 `completion_window`、减任务数、
换模型 —— 都不行。

### 排查过程（这才是值得记的部分）

1. 先做**浅探测**（只上传文件，不建批次）→ 通过，说明地址和 Key 没问题；
2. 再做**深探测**（真建批次）→ 500；
3. 于是写了一个「参数组合矩阵」：`completion_window` × 是否带 `metadata` × 是否带 `name`……
   逐个组合试；
4. **最后在小米控制台的返回体里看到 `"name":"test"`** —— 控制台自己建的任务带了这个字段。
   补上 `name` 之后**一次就过**。

### 根因

**创建批次必须带 `name` 字段，但官方文档里没有写。**

### 修复

```js
name: batchNameOf(kind),   // "Solace·内容审核" / "Solace·日记打标" / "Solace·日记生成"
```

⚠️ 官方文档里写着必填的 `name` 👈 —— **反过来，文档没写的也可能是必填的**。

### 预防措施

- 报错信息里带上**"我们到底发了什么"**：接口路径、`completion_window`、任务数（含图片数）、文件 id。
  上游只回 `internal_error` 时，没有这些参数根本没法定位；
- 后台的「测试批量接口」现在会**逐个组合探测并把 JSONL 原文回显**，下次上游再改协议能立刻看出来。

## INC-008｜PM2 重启了 208 次，日志里却没有任何报错

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | `pm2 list` 里 `↺` 计数已经 208 次 |
| **严重程度** | **中**（表现为"偶尔卡一下"，容易被忽略） |
| **是否丢数据** | 否 |

### 现象

服务隔一阵就重启，但 `pm2 logs` 里看不到任何异常堆栈。

### 根因

**两个内存参数不匹配**：

| 参数 | 值 | 含义 |
|---|---|---|
| Node 的 V8 堆上限 | 约 **1.8G** | 超过它 Node 自己会 OOM |
| PM2 的 `max_memory_restart` | **600M** | 超过它 PM2 主动把进程杀掉重启 |

程序还在 V8 的舒适区（比如 700M）时，PM2 就已经认为"它吃太多了"，直接杀掉重启。
**不是崩溃，是被"预防性"杀掉。**

### 修复

两个值**一起调、并且对齐**：

```js
node_args: "--max-old-space-size=450",   // 让 Node 主动控制在这个水位
max_memory_restart: "700M",              // PM2 的阈值留在它之上
```

### 预防措施

⚠️ **这两个值必须成对设置**。只设 `max_memory_restart` 而不给 Node 一个明确上限，
就是给未来的自己埋雷 —— 而且它不会报错，只会安静地重启。

## INC-009｜「我tm草泥马，你个废物，臭sb」整句一个都没拦住

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 用自己的话测审核词表，一句典型的脏话 0 命中 |
| **严重程度** | **中**（审核形同虚设） |
| **是否丢数据** | 否 |

### 现象

第一次测试词表时，`fuck` 没拦住 —— 因为提示词里只写了"人身攻击"，漏了"脏话本身"。
补完提示词后，用中文样本再测，**整句一个词都没命中**。

### 根因

词表里只有**规范写法**。而真实输入里是：

- 拼音首字母缩写：`sb` / `tm` / `tmd` / `nmsl` / `cnm` / `mdzz`
- 各种变体与谐音
- 中间夹着别的字（`我tm草泥马`）

### 修复

按两个维度重列：

1. **家族** —— 同一个词的所有常见写法归到一起（草泥马 / 草泥馬 / 卧槽 / 我操…）；
2. **拼音缩写单列** —— ⚠️ 这几个**必须用词边界匹配**，否则 `sb` 会命中 `absorb`、`tm` 会命中 `atm`。

### 预防措施

**用真实样本测词表，不要用自己造的例子** —— 造例子时会不自觉地把词写成规范形式，
而那恰好是词表覆盖得最好的情况。

## INC-010｜审核 AI 读不懂格式时，曾经的默认行为是"按通过处理"

| 项 | 内容 |
|---|---|
| **发生时间** | 2026-09 |
| **发现方式** | 用户在验收时指出："读不懂就当通过，这不是等于不审吗" |
| **严重程度** | **中高**（可能放过违规内容 —— 属于设计缺陷，不是实现 bug） |
| **是否丢数据** | 否 |

### 现象

AI 返回的内容不符合约定格式时，代码打一行日志"AI 返回的不是约定格式，按通过处理"，然后放行。

### 根因

**默认值的方向错了。** 审核这种系统，遇到"判断不了"的情况，
默认必须是**更保守的那一侧**（交人工），而不是更省事的那一侧（放行）。

### 修复

判定的返回值从两态改成**三态**：

```
明确 pass   → 清掉「未审核」标记
明确 reject → 回填默认值
读不懂      → 标 failed，进人工队列
```

### 预防措施

⚠️ **审核类系统的默认分支必须是"不确定"**。写这类代码时问自己一句：

> 如果这一段永远走不到正常路径、只能走默认分支，最坏结果是什么？

如果答案是"违规内容被放行"，那这个默认值就是错的。

## 记录规范

新增记录时按上面的结构写，并在表头标注**时间 / 严重程度 / 是否丢数据**。
标题用一句话说清"谁坏了"，不要只写编号。

⚠️ 特别值得记的两类：

1. **排查过程很长、但根因只有一行的**（如 INC-007）—— 下次遇到类似现象能立刻联想到；
2. **不是"代码写错了"而是"默认值/方向选错了"的**（如 INC-010）—— 这类最容易复发，
   因为改完那一行代码就看不出来了，只有把判断依据写下来才防得住。
