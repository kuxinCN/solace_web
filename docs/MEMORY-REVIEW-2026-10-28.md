# 暖言 · 长期记忆系统 工程审查报告

- 日期：2026-10-28
- 范围：`lib/memory-*`、`app/api/user/memories/*`、`app/api/chat/route.js`、`lib/scheduler.js`、`components/MemoriesModal.jsx`、相关 schema
- 结论：**四批优化全部落地并通过构建/静态检查/接口实测；建议在此版本收口，其余列为观察项。**

## 一、结论摘要

本次把记忆系统从"关键词命中一句话才记"升级为一条完整链路：

```
写入：批量提炼（最近 8 条对话） + 模型自主 [MEMORY:] + T+1 日报 + 超量自动压缩
维护：近似去重 / 重复提及强化 / 状态变更失效（可恢复）
读取：最近 3 条用户消息做相关性 + 关系偏好常驻 + 画像/日报背景 + 800 字预算
管理：记忆库分类筛选 / 编辑 / 删除（回收站）/ 恢复失效
```

与 GPT 记忆模式的对照：

| 能力 | 当前实现 | 状态 |
|---|---|---|
| 自动积累 | 三通道写入 + 每日汇总 + 超量压缩 | ✅ |
| 用户可见、可改、可删 | 记忆库：分类筛选 / 编辑 / 删除进回收站 / 恢复失效 | ✅ |
| 冲突/过期处理 | 六类状态变化 → 旧记忆标记失效（只标记不删除） | ✅（启发式） |
| 容量控制 | >150 条自动压缩最旧 40 条为画像总结 | ✅（未真机联调） |
| 跨对话检索 | 事实池 200 + 最近 3 条用户消息相关性 + 核心事实常驻 | ✅（字面匹配，非语义） |
| 语义检索 | 未引入向量/embedding | ❌（可选） |

## 二、现状架构

### 2.1 写入

| 通道 | 触发 | 输入 | 产出 | 频率控制 |
|---|---|---|---|---|
| ① 批量提炼 | 流式回复结束后 fire-and-forget | 最近 8 条对话 | 0~3 条，五类分行（≤80 字/条） | 前端 10 分钟或 5 条用户消息；后端 3 分钟/userId，且**成功写库后才占位** |
| ② 模型自主 | `[MEMORY:...]` 标记（服务端强制注入规则） | 模型回复 | 1 条，category=self | 由模型自行判断 |
| ③ 每日汇总 | 调度器每天一次 | 前一天对话（≤120 条/6000 字） | 1 条 daily（≤200 字） | 日期槽 + DB 去重 |
| ④ 自动压缩 | 调度器每天一次，活跃事实 >150 | 最旧 40 条 event/emotion/self/未分类 | 1 条 profile（≤200 字），原文转失效 | 每用户每天一次；每天最多 20 人 |

### 2.2 读取（每次聊天）

```
loadMemoryCandidates(userId)      并行三查：profile(1) + daily(2) + facts(200)
selectMemoryRows(...)             bigram 相关性打分；核心事实常驻 ≤4；无关时留最近 6
buildMemoryMessage(rows)          800 字预算；从末尾（最相关）向前装，先丢背景
```

注入顺序（越靠后越贴近用户消息、注意力越高）：`profile → daily → 常驻事实 → 最相关事实`。

### 2.3 关键参数

| 参数 | 值 | 位置 |
|---|---|---|
| 事实候选池 | 200 | `memory-store.js` |
| 相关事实上限 / 兜底 | 14 / 6 | 同上 |
| 常驻核心事实 | 4 | 同上 |
| 注入总字数 | 800 | 同上 |
| 提炼批量窗口 | 8 条 | `page.js` |
| 提炼闸门 | 10 分钟 / 5 条用户消息 | `page.js` |
| 后端冷却 | 3 分钟 / userId | `extract/route.js` |
| 压缩阈值 / 单批 / 用户上限 | 150 / 40 / 20 | `memory-compact.js` |

## 三、本次四批改动

### 第 1 批：可编辑 + 分类标注

- 新增 `PATCH /api/user/memories`（改内容 / 改分类 / 恢复），`WHERE user_id` 防越权；空内容 400、不存在 404。
- 记忆库：内联编辑、分类徽标、分类筛选（只显示有数据的分类）、筛选内全选/批量删除。
- 修复：PATCH 用 `affectedRows` 判存在 → 值未变化时误报 404，改为执行后 SELECT。

### 第 2 批：状态变更失效

- 新增 `lib/memory-conflict.js`：分手/离婚、辞职/换工作、搬家/换城市、不养宠物、戒烟戒酒、毕业退学。
- 命中后旧记忆 `superseded_at=NOW()`；读取端过滤；记忆库显示「已失效」+ 恢复；不物理删除。
- 反例保护：`我朋友分手了`、`我妈离婚了` 不触发。

### 第 3 批：跨对话检索

- 查询文本改为最近 3 条**用户**消息（排除 AI 复述造成的自证相关）。
- 候选池 100 → 200；关系/偏好常驻 ≤4。
- 修复预算裁剪方向：原实现从头装、超 800 字 break，**先丢最相关**；改为从末尾往前装。

### 第 4 批：自动压缩

- 新增 `lib/memory-compact.js`；调度器每日槽内执行。
- 只压 `event/emotion/self/未分类`；`relation/preference` 保留原文。
- **三步安全顺序**：① AI 生成总结 → ② 写库并 `SELECT` 回查确认画像有效 → ③ 才用**一条原子 UPDATE** 标记旧记忆失效。任何一步失败（AI 报错 / 空 / NONE / 总结被去重 / 查不到画像 / 数据库断开）都**停在原地，一条旧记忆都不动**。
- 注入端新增 profile（最新 1 条，置于最前）。
- **手动触发**：`POST /api/admin/memories/compact`（后台登录态）——`{ userId, force: true, batch: 3 }` 可只压指定用户、跳过 150 条阈值；不带 `userId` 等于手动跑一次调度器那轮扫描。

### 数据库变更

| 变更 | 迁移方式 | 幂等 |
|---|---|---|
| `assessment_results.type` 16 → 64 | `ensureUserColumnsOnce()` 内查 `information_schema` 后 ALTER | ✅（长度已够则跳过） |
| `user_memories.superseded_at` DATETIME NULL | `ensureMemoryColumns()` 补列 | ✅（`addMissingColumns` 查列） |

## 五、风险与已知限制

1. **压缩未真机验证**：需要可用 AI Key 与超阈值数据。失败路径已设计为"只读"，不会破坏已有记忆。
2. **冲突规则是启发式**：只覆盖六类状态变化，且要求第一人称；仍可能误判。因此采用"标记失效 + 可恢复"，不做删除。
3. **相关性是字面匹配**（bigram），不是语义检索：同义表达（"加班" vs "工作到很晚"）可能命中不到。
4. **800 字预算**仍是硬顶：记忆特别丰富的用户，注入内容会以"背景先让位"的方式裁剪。
5. **冷却与闸门状态**：前端在 localStorage、后端进程内 Map —— 重启/多实例会重置（设计上可接受，但多实例部署时冷却不严格）。
6. **记忆库一次最多 200 条**，无分页/搜索。
7. **未做观测指标**：注入命中率、平均注入条数、压缩触发次数目前只能看日志。

## 六、部署与升级注意

1. 升级后必须 **重启进程**，并访问一次会触发 `ensureUserColumnsOnce()` 的接口（日记 / 记忆 / 后台任意页），列变更才会执行；只 `GET /api/user/profile` 不会触发（仅 PUT 会）。
2. 构建判据是 **退出码 0 + Route 表**，不是 `✓ Compiled successfully`。
3. 压缩与日报共用日期槽：进程重启当天会再跑一次；`saveMemory` 去重 + 原文已失效，不会膨胀。
4. 不要同时跑 dev 与 build（共用 `.next`）。

## 七、后续可选优化（非必须）

| 优先级 | 方向 | 说明 | 成本 |
|---|---|---|---|
| P1 | 语义检索 | 引入 embedding（或轻量向量库），解决同义表达命中 | 中高（新增依赖/存储/回填） |
| P1 | 模型判定冲突 | 用模型替代正则判断"旧记忆是否失效"，更准但多一次调用 | 中 |
| P2 | 记忆库搜索/分页 | 200 条以上可用 | 低 |
| P2 | 观测指标 | 注入条数、命中率、压缩次数写入统计页 | 低 |
| P3 | 手动置顶/导入导出 | 让用户固定关键事实、迁移数据 | 中 |

**建议**：先积累 1~2 周真实使用数据，确认"该记的记了、该想起的想起了"，再决定是否投入语义检索。
